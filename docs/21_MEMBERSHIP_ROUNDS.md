## 1. ปัญหาที่แก้

โจทย์จากอาจารย์: **"early bird" ต้องแปลว่าสมาชิกได้ *กดก่อน* ไม่ใช่ได้ *ลดราคา***

ระบบเดิมมีสวิตช์เดียวคือ `Concert.status = ON_SALE` — พอเปิดขาย ทุกคนเข้าพร้อมกันหมด
ไม่มีทางบอกได้ว่า "ช่วงครึ่งชั่วโมงแรกให้เฉพาะสมาชิก" ซึ่งเป็นวิธีที่ผู้ขายบัตรจริงใช้กัน
(ไทยทิคเก็ตเมเจอร์, Thaiticketmajor presale, Ticketmaster Verified Fan ล้วนเป็นรอบเวลาแยก)

ต้องได้ 2 อย่างพร้อมกัน:
1. มีสถานะ "สมาชิก" ที่แอดมินให้/เพิกถอนได้ และผู้ใช้สมัครเองได้
2. คอนเสิร์ตตั้งรอบได้ว่าช่วงไหนใครกดได้ โดย**ของเก่าที่ไม่ได้ตั้งรอบต้องไม่พัง**

## 2. การตัดสินใจที่สำคัญที่สุดในฟีเจอร์นี้

### 🔑 "สมาชิกกดก่อน" ทำเป็น **รอบเวลาแยก** ไม่ใช่ให้แซงคิว

ทางเลือกที่ **ตัดทิ้ง**: ทำคิวแบบมีลำดับความสำคัญ (priority queue) ให้สมาชิกได้คะแนนคิวดีกว่าในรอบเดียวกัน

เหตุผลที่ตัด — **มันจะทำลายผลวิจัยในเล่ม**:
บทที่วัดความเป็นธรรมของคิว (fairness) ตั้งอยู่บนสมมติฐานว่า **คิวเป็น FIFO + สุ่ม ไม่มีใครแซงได้**
ถ้าใส่ลำดับความสำคัญเข้าไป ตัวเลขความเป็นธรรมทั้งบทต้องวัดใหม่หมด และจะอธิบายยากขึ้นมากว่า
"เป็นธรรม" แปลว่าอะไรเมื่อบางคนมีแต้มต่อ

ทำเป็นรอบเวลาแทน → **ภายในรอบเดียวกัน คิวยังเป็นธรรมเป๊ะเหมือนเดิม**
สมาชิกได้เปรียบที่ "เข้าประตูได้เร็วกว่า" ไม่ใช่ "แซงคนที่อยู่ในห้องเดียวกัน"
สถิติ fairness ที่วัดไว้แล้วยังใช้ได้ทั้งหมด ไม่ต้องรันใหม่

### 🔑 หมดอายุ **คำนวณสด** ไม่ใช่มี cron มาพลิกสถานะ

`isMembershipActive()` ตัดสินจาก `status` + `expiresAt` เทียบกับเวลาปัจจุบัน**ทุกครั้งที่ถาม**

ทางเลือกที่ตัดทิ้ง: มี cron รายวันไล่เปลี่ยน `status` ของแถวที่หมดอายุเป็น `EXPIRED`

เหตุผล — นี่คือ bug คลาสหนึ่งที่เจอบ่อยและแก้ยาก: **ระหว่างที่ cron ยังไม่วิ่ง ข้อมูลจะผิด**
สมาชิกที่หมดอายุเมื่อวานยังกดบัตรได้ถ้า cron ตกรอบ หรือ cron ตายเงียบ ๆ ไปหลายวันโดยไม่มีใครรู้
ระบบนี้มี cron อยู่แล้วตัวหนึ่ง (`/api/cron/sweep`) และรู้ดีว่ามันตกรอบได้

ผลที่ตามมาที่ต้องรู้: **แถวที่ `status = ACTIVE` อาจไม่ใช่สมาชิกแล้วก็ได้**
ห้ามอ่าน `status` ตรง ๆ มาตัดสินสิทธิ์ที่ไหนเลย ต้องผ่าน `isMembershipActive()` / `describeMembership()` เสมอ
มีเทสหน่วยคุมข้อนี้โดยเฉพาะ (แถวเดียวกัน ถามคนละเวลา ต้องได้คำตอบต่างกัน)

### 🔑 เพิกถอนแล้ว **ไม่ลบแถวทิ้ง**

`revokeMembership()` ตั้ง `status = REVOKED` + `revokedAt` ไม่ใช่ `delete`
เพื่อให้ตอบได้ว่าใครเคยมีสิทธิ์ ใครถอนเมื่อไหร่ — สำคัญตอนมีคนทักว่า "ทำไมกดไม่ได้"

## 3. Schema ที่เพิ่ม

migration: `20260818093203_phase2_seatmap_membership_sale_round`

### `Membership` (1 แถวต่อ 1 ผู้ใช้ — `userId` เป็น unique)

| field | ความหมาย |
|---|---|
| `status` | `ACTIVE` \| `REVOKED` — **ไม่มี `EXPIRED`** เพราะหมดอายุคำนวณสดจาก `expiresAt` |
| `source` | `SELF_SIGNUP` \| `ADMIN_GRANT` — มาจากไหน |
| `startedAt` | เริ่มมีสิทธิ์เมื่อไหร่ |
| `expiresAt` | `null` = ไม่มีกำหนดหมดอายุ |
| `grantedByUserId` | แอดมินคนไหนให้ (null ถ้าสมัครเอง) |
| `revokedAt` | เพิกถอนเมื่อไหร่ |

### `SaleRound` (หลายรอบต่อ 1 คอนเสิร์ต)

| field | ความหมาย |
|---|---|
| `concertId` | เจ้าของรอบ — ลบคอนเสิร์ต รอบหายตาม (Cascade) |
| `name` | ชื่อที่โชว์ผู้ใช้ เช่น "รอบสมาชิก" |
| `audience` | `MEMBER_ONLY` \| `PUBLIC` |
| `startAt` / `endAt` | ช่วงเวลาของรอบ |

### `Order.saleRoundId` (nullable)

บันทึกว่าคำสั่งซื้อนี้เกิดในรอบไหน — **ใช้ทำสถิติ/ตรวจสอบย้อนหลังอย่างเดียว
ไม่มี logic ไหนอ่าน field นี้มาตัดสินใจ** เพดานตั๋วยังนับรวมทุกรอบต่อคอนเสิร์ตเหมือนเดิม

`onDelete: SetNull` — ลบรอบแล้วคำสั่งซื้อไม่หาย แค่เสียข้อมูลว่ามาจากรอบไหน
(ถึงอย่างนั้นก็ยังกันไม่ให้ลบรอบที่มีคำสั่งซื้อ — ดู §6.3)

## 4. กติกาการตัดสินสิทธิ์ — `resolveSaleAccess()`

ทั้งไฟล์ `lib/sale-round.ts` เป็น **pure function ล้วน** ไม่แตะฐานข้อมูล ไม่อ่านนาฬิกาเอง (รับ `now` เข้ามา)
→ เทสกำหนดเวลาได้เอง และไม่มีเทสที่ผลเปลี่ยนตามเวลาที่รัน

```
ไม่มีรอบเลย                          → ผ่าน (พฤติกรรมเดิมก่อนมีฟีเจอร์นี้)
มีรอบที่เปิดอยู่ และคนนี้เข้าได้      → ผ่าน
มีรอบที่เปิดอยู่ แต่เป็นรอบสมาชิก     → ปฏิเสธ MEMBER_ONLY + บอกเวลารอบทั่วไป
ยังไม่ถึงรอบที่คนนี้เข้าได้           → ปฏิเสธ NOT_STARTED + บอกเวลาเปิด
ไม่มีรอบไหนที่คนนี้เข้าได้อีกแล้ว     → ปฏิเสธ ENDED
```

### จุดที่ต้องอธิบาย (ไม่ obvious)

**ช่วงเวลาเป็นแบบ `[เริ่ม, จบ)`** — เวลา `จบ` พอดีถือว่า**ออกจากรอบแล้ว**
เพื่อให้ตั้งรอบต่อกันได้ตรง ๆ (รอบสมาชิกจบ 19:30, รอบทั่วไปเริ่ม 19:30)
โดยไม่มีทั้งช่องว่างและช่วงทับซ้อน ถ้าใช้ `[เริ่ม, จบ]` ทั้งสองด้าน วินาทีที่ 19:30:00 จะอยู่ในสองรอบพร้อมกัน

**รอบทับกัน ให้ยึดรอบที่ผ่อนปรนที่สุด** — ถ้าเวลานี้อยู่ในหลายรอบ ขอแค่มีรอบเดียวที่คนนี้เข้าได้ก็ผ่าน
เหตุผล: แอดมินตั้งรอบทับกันโดยไม่ตั้งใจเป็นเรื่องที่เกิดได้ง่ายมาก
ผลที่ควรได้คือ "เข้าได้" ไม่ใช่ "ทุกคนเข้าไม่ได้เพราะแอดมินกรอกเวลาพลาด"

**`nextOpenAt` คือรอบถัดไปที่ *คนนี้* เข้าได้ ไม่ใช่รอบถัดไปเฉย ๆ**
คนทั่วไปที่โดนปฏิเสธตอนรอบสมาชิก ต้องได้เวลาของ**รอบทั่วไป**
ถ้าบอกเวลารอบสมาชิกรอบถัดไป เขาจะกลับมากดแล้วโดนปฏิเสธซ้ำ — เป็นการโกหกผู้ใช้

## 5. บังคับใช้ 3 จุด (ไม่ใช่จุดเดียว)

| จุด | ไฟล์ | ทำไมต้องมี |
|---|---|---|
| **1. เข้าคิว** | `app/api/queue/join/route.ts` | ประตูบานแรกจริง ๆ ของการซื้อ — ยิง API ตรงข้ามหน้าเว็บก็ต้องโดนกัน |
| **2. หน้าเลือกที่นั่ง** | `app/(public)/concerts/[slug]/seats/page.tsx` | **รอบอาจปิดระหว่างที่ผู้ใช้ยังถือ queue token อยู่** ถ้าเช็คแค่ตอนเข้าคิว คนที่ผ่านคิวไปตอนรอบสมาชิกจะซื้อข้ามรอบได้ |
| **3. ยืนยันจอง** | `app/actions/booking.ts` | ด่านสุดท้ายก่อนสร้างคำสั่งซื้อจริง + เป็นที่ที่บันทึก `saleRoundId` |

ทุกจุดเรียกผ่าน `checkSaleAccess()` ตัวเดียวกัน (`lib/sale-round-guard.ts`) → กติกาไม่มีทางเพี้ยนกันเอง

**ด่านรอบวางไว้ก่อน anti-bot ในไฟล์ route** โดยตั้งใจ — คนที่ยังไม่ถึงรอบไม่ควรต้องไปแก้ CAPTCHA
ก่อนแล้วค่อยมารู้ว่าเข้าไม่ได้อยู่ดี

**รอบเป็นด่านซ้อนทับ `ON_SALE` ไม่ได้มาแทน** — คอนเสิร์ตต้องเปิดขายก่อน รอบถึงจะมีความหมาย

## 6. ด่านความปลอดภัย

### 6.1 สิทธิ์แอดมิน
`createSaleRound` / `updateSaleRound` / `deleteSaleRound` / `grantMembership` / `revokeMembership`
เรียก `assertVerifiedAdmin()` ซึ่ง**อ่าน role จากฐานข้อมูลใหม่ทุกครั้ง ไม่เชื่อ JWT**
(คนที่ถูกถอดสิทธิ์แอดมินแต่ token เก่ายังไม่หมดอายุ ต้องใช้ไม่ได้ทันที)

### 6.2 กันยิงข้ามคอนเสิร์ต
`updateSaleRound` / `deleteSaleRound` เช็คว่า `round.concertId` ตรงกับ `concertId` ที่ส่งมาจริง
รหัสรอบเป็นเลขเรียงเดาได้ ถ้าไม่เช็คจะแก้/ลบรอบของคอนเสิร์ตอื่นได้ด้วยการเดาเลข

### 6.3 ลบรอบที่มีคำสั่งซื้อไม่ได้
ถ้ามี `Order` ผูกอยู่ จะปฏิเสธพร้อมบอกจำนวนรายการ
เพราะ `SetNull` ทำให้ลบได้แบบไม่พังข้อมูล แต่**สถิติ "ยอดขายรอบสมาชิก vs รอบทั่วไป" จะหายถาวร**
ซึ่งเป็นตัวเลขที่จะใช้ในเล่ม — แนะนำให้แก้เวลารอบแทนการลบ

### 6.4 เพดานจำนวนรอบ
สูงสุด 20 รอบต่อคอนเสิร์ต — กันตั้งรอบเป็นร้อยจนหน้าจอและด่านตรวจช้า

### 6.5 อายุสิทธิ์ที่ให้ได้
สูงสุด 3650 วัน (10 ปี), `0` = ไม่มีกำหนด — กันกรอกเลขมั่วจนล้น

## 7. 🔴 กับดักโซนเวลา (จุดที่พังเงียบที่สุด)

`<input type="datetime-local">` คืนค่าเป็นสตริง**ไม่มีโซนเวลาติดมา** เช่น `"2026-08-25T19:00"`

ถ้าส่งสตริงนี้ให้เซิร์ฟเวอร์ `new Date()` ตรง ๆ เซิร์ฟเวอร์จะตีความเป็นเวลาท้องถิ่น**ของเซิร์ฟเวอร์**
- รันในเครื่องตัวเอง (โซนไทย) → **ถูก** จึงไม่มีใครเห็นปัญหาตอนพัฒนา
- ขึ้น Vercel (โซน UTC) → **รอบเลื่อนไป 7 ชั่วโมง** รอบสมาชิกที่ตั้งไว้สองทุ่มไปเปิดตอนตีสาม

วิธีแก้: **แปลงเป็น ISO ตั้งแต่ฝั่งเบราว์เซอร์** ซึ่งเป็นที่เดียวที่รู้โซนเวลาจริงของแอดมิน
(`components/sale-round-editor.tsx` → `localInputToIso()`)

เทส integration มีข้อที่จับเรื่องนี้โดยเฉพาะ: กดปุ่ม "เติมเวลาสาธิต" (เริ่มเดี๋ยวนี้ + 30 นาที)
แล้ว**เทียบเวลาที่ลง DB จริงกับเวลาที่กด** ถ้าแปลงผิดโซนจะห่างกันเป็นชั่วโมง เทสตกทันที

## 8. Flow การใช้งาน

### แอดมิน
1. `/admin/members` → ให้สิทธิ์ (เลือก 30 วัน / 1 ปี / ไม่มีกำหนด) หรือเพิกถอน
2. `/admin/concerts/{id}/rounds` → เพิ่มรอบสมาชิก (ปุ่ม **"เติมเวลาสาธิต"** ตั้งเริ่มเดี๋ยวนี้ 30 นาทีให้ในคลิกเดียว)
3. เพิ่มรอบทั่วไปต่อท้าย โดยตั้งเวลาเริ่ม = เวลาจบของรอบสมาชิก
4. กด "เปิดขาย" ที่หน้าคอนเสิร์ต (รอบไม่มีผลถ้ายังไม่ `ON_SALE` — มีป้ายเตือนบนหน้าตั้งรอบ)

### คนซื้อ
1. หน้ารายละเอียดคอนเสิร์ต เห็น**ตารางรอบ**ว่ารอบไหนเปิดกี่โมง รอบไหนของใคร + ป้าย "กำลังเปิด"
2. ไม่ใช่สมาชิก + อยู่ในรอบสมาชิก → กดเข้าคิวแล้วถูกปฏิเสธพร้อมข้อความว่ารอบทั่วไปเปิดกี่โมง
3. `/account/membership` → รับสิทธิ์สมาชิก (1 ปี) แล้วกดเข้าคิวได้ทันที ไม่ต้องรออะไร

**หมายเหตุการออกแบบ:** ตารางรอบบนหน้ารายละเอียดคอนเสิร์ตจงใจ**ไม่บอกว่า "คุณ" เข้าได้ไหม**
เพราะหน้านั้นตั้ง `revalidate = 60` (แคชทั้งหน้า) — เป็นหน้าที่โดนถล่มหนักสุดตอนเปิดขาย
ถ้าดึง session มาแสดง Next จะเปลี่ยนหน้าเป็น dynamic ทันที = แคชหายทั้งหน้า
คำตัดสินรายคนไปอยู่ที่ด่านจริง (หน้าเข้าคิว / หน้าเลือกที่นั่ง) แทน

ป้าย "กำลังเปิด" คำนวณ**หลังหน้าโหลดเสร็จเท่านั้น** ไม่ใช่ตอนเรนเดอร์ ไม่งั้นสถานะจะถูกแคชไปด้วย
แล้วคนที่เปิดหน้าทีหลังจะเห็นป้ายเก่าค้างได้ถึง 60 วินาที

3. คนทั่วไปถูกปฏิเสธตอนรอบสมาชิก ด้วยเหตุผล `MEMBER_ONLY`
4. `nextOpenAt` ที่ตอบกลับ**ตรงกับเวลาเริ่มรอบทั่วไปเป๊ะ** (ไม่ใช่แค่ "มีค่าอะไรสักอย่าง")
5. **หน้าเลือกที่นั่งกันด้วย** ไม่ใช่กันแค่ API
6. แอดมินให้สิทธิ์ → คนเดิมผ่านด่านทันที ไม่ต้องรอ cron/รีสตาร์ท
7. เพิกถอน → กดไม่ได้ทันที และแถวยังอยู่ (ไม่ลบประวัติ)
8. ลบรอบที่มีคำสั่งซื้อไม่ได้ + แอดมินเห็นเหตุผล
9. **คอนเสิร์ตที่ไม่ได้ตั้งรอบ ใครก็กดได้เหมือนเดิม** (ของเก่าไม่พัง)

### สองเรื่องที่ตั้งใจทำต่างจากปกติ

**ไม่เดินผ่านห้องรอในเบราว์เซอร์** — หน้านั้นมี Turnstile ของจริง และการไปแก้ CAPTCHA ด้วยสคริปต์
คือสิ่งที่ทั้งระบบนี้สร้างมาเพื่อกัน เทสจึงยิง `/api/queue/join` ตรง ๆ ด้วย cookie ของ session จริงแทน
(ด่านรอบอยู่ก่อน anti-bot ในไฟล์ route อยู่แล้ว จึงทดสอบได้ครบโดยไม่ต้องแตะ CAPTCHA)

**ไม่ยืนยันด้วย `status === 200` ในเคส "ผ่าน"** — เพราะผ่านด่านรอบแล้วยังต้องไปเจอ anti-bot ต่อ
ซึ่งอาจตอบ 428 ขอให้ทำ Turnstile ตามสภาพ key ที่ตั้งไว้ในเครื่องนั้น
เทสจึงยืนยันเจาะจงว่า "ไม่ได้ถูกปฏิเสธด้วยเหตุผลเรื่องรอบ" — ตรงกับสิ่งที่เทสนี้อ้างว่าพิสูจน์

### บั๊กที่เทสจับได้จริง (ไม่ใช่เทสที่เขียนตามโค้ด)

กดลบรอบที่มีคำสั่งซื้อ → ระบบปฏิเสธถูกต้อง แต่**หน้าจอเงียบสนิท** แอดมินจะนึกว่าปุ่มเสีย
สาเหตุ: ที่แสดงข้อความผิดพลาดอยู่ในฟอร์มที่ตอนนั้นยังไม่ได้เปิด → ย้ายออกมาให้แสดงได้เสมอ

## 10. ข้อจำกัดที่รู้อยู่และยอมรับ

| ข้อจำกัด | ทำไมยอมรับ |
|---|---|
| สมาชิกสมัครเองได้ฟรี ไม่มีการเก็บเงิน | ระบบสาธิต — ถ้าจะเก็บเงินต้องต่อ flow จ่ายเงินเข้ากับ `Membership` ซึ่งอยู่นอกขอบเขต |
| ไม่มีระดับสมาชิก (เงิน/ทอง/แพลทินัม) | โจทย์ต้องการแค่ "สมาชิก vs ไม่ใช่สมาชิก" — เพิ่มระดับทีหลังได้โดยเติม `audience` เป็นชนิดใหม่ |
| ไม่มีอีเมลแจ้งเตือนก่อนรอบเปิด | ยังไม่จำเป็นต่อการสาธิต |
| `Order.saleRoundId` ยังไม่มีหน้าสรุปยอดขายรายรอบ | ข้อมูลถูกเก็บครบแล้ว ทำหน้าสรุปเมื่อไหร่ก็ได้ |
| หน้ารายละเอียดคอนเสิร์ตไม่บอกสิทธิ์รายคน | ตั้งใจ เพื่อรักษาแคชของหน้าที่โดนถล่มหนักสุด (ดู §8) |
