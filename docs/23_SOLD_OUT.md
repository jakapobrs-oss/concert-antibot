# 23 — บัตรหมด (SOLD OUT) + รอบมาตรฐานแบบผังคอนไทย

> สถานะ: **โค้ดเสร็จ + ทดสอบบนเครื่องจริงแล้ว** · เขียน 2026-08-20
> ต่อจาก [21_PRESALE_ROUNDS.md](21_PRESALE_ROUNDS.md) — ไฟล์นั้นคือ "ใครกดได้รอบไหน" ไฟล์นี้คือ **"ถ้าบัตรหมดก่อนถึงรอบถัดไปแล้วยังไง"**

---

## 1. โจทย์จากพฤติกรรมจริง

ลำดับที่ผังคอน/เอเจนซี่ไทยทำจริง:

```
ประกาศวันแสดง → ประกาศวันเปิดจอง → รอบสมาชิกกดก่อน 1–3 วัน → รอบทั่วไป
                                            │
                                            └─ ถ้าบัตรหมดตรงนี้ → ประกาศ SOLD OUT
                                               รอบทั่วไป "ไม่เปิดขาย" ทั้งที่ยังไม่ถึงวันตามประกาศ
```

สิ่งที่ระบบเดิม (ก่อนรอบนี้) ทำผิดจากความจริง 2 ข้อ:

1. **ไม่มีใครประกาศบัตรหมด** — `Concert.status = SOLD_OUT` มีในฐานข้อมูล แต่ไม่มีโค้ดไหนตั้งค่าให้เลย
   ต้องรอแอดมินมากดเอง ซึ่งในงานจริงช้ากว่าความเป็นจริงหลายชั่วโมง
2. **รอบทั่วไปยังโชว์ว่า "ยังไม่เริ่ม"** ทั้งที่ไม่มีบัตรเหลือให้ขายแล้ว → ผู้ใช้เฝ้ารอเก้อ

---

## 2. นิยาม "บัตรหมด" ที่ระบบใช้

```
available = ที่นั่ง AVAILABLE  (เลือกได้ตอนนี้)
held      = ที่นั่ง HELD       (อยู่ในหน้าจ่ายเงินของคนอื่น อีก 5 นาทีอาจหลุดกลับมา)

soldOut   = available = 0  และ  held = 0
```

**ทำไมต้องนับ `held` ด้วย** — ถ้าประกาศ SOLD OUT ตอน `available = 0` เฉย ๆ แล้วมี hold ค้างอยู่
พอ hold หมดอายุที่นั่งจะไหลกลับมาเป็น AVAILABLE แต่ป้าย "บัตรหมด" ประกาศไปแล้ว = ระบบโกหกผู้ใช้
ช่วงที่ `available = 0` แต่ยังมี `held` ระบบถือว่า **"เต็มชั่วคราว"** ไม่ใช่หมด (`isTemporarilyFull`)

---

## 3. ประกาศเองอัตโนมัติ ตอนไหน

| จุด | ทำอะไร |
|---|---|
| หลังออกตั๋วสำเร็จ (`finalizePaidOrder`) | เรียก `syncSoldOutStatus()` — ที่นั่งเพิ่งกลายเป็น SOLD จริงตรงนี้จุดเดียว |
| ตอนผู้ใช้เปิดหน้าคอนเสิร์ต / เรียก API รอบ | คำนวณสดจากจำนวนที่นั่ง (ไม่รอสถานะใน DB) |
| ตอนขอเข้าคิว | ปฏิเสธด้วยข้อความ "บัตรหมดแล้ว" (`action: SOLD_OUT`) — **ทุกคอนเสิร์ตรวมที่ไม่มีรอบขาย** (แก้ 2026-08-26, ดู §8) |
| ตอนอยู่ในคิวแล้ว | สถานะคิวตอบ `SOLD_OUT` → ห้องรอหยุด poll + "บัตรหมดแล้ว" + ปุ่มกลับหน้าคอนเสิร์ต (§8) |

**ทิศทางเดียว: `ON_SALE → SOLD_OUT` เท่านั้น**
การเปิดขายใหม่ (เช่นมีคนคืนบัตรตาม [docs/19](19_NAMED_TICKET_PLAN.md)) เป็น**การตัดสินใจของผู้จัด** ระบบไม่พลิกกลับเอง
ไม่งั้นบัตรคืนใบเดียวจะทำให้ประกาศ SOLD OUT ที่ออกไปแล้วกลับมาเปิดขายเงียบ ๆ — แอดมินเปลี่ยนสถานะเองได้ที่หน้าแอดมิน

การอัปเดตสถานะถูกห่อ `try/catch` แยกจากทรานแซกชันออกตั๋ว — **การติดป้ายสถานะห้ามทำให้ "จ่ายเงินแล้วออกตั๋วสำเร็จ" กลายเป็นล้มเหลว**

## 4. ผลกับรอบขาย

| สถานการณ์ | ก่อนแก้ | หลังแก้ |
|---|---|---|
| บัตรหมดตอนรอบสมาชิก · คนทั่วไปเปิดหน้าคอนเสิร์ต | "รอบทั่วไป เริ่ม 24 ส.ค. 11:46" (ให้ความหวังผิด ๆ) | **"บัตรหมดแล้ว (SOLD OUT)"** + รอบทั้งหมดขึ้น "ไม่เปิดขาย — บัตรหมดก่อน" |
| สมาชิกที่มีสิทธิ์กดอยู่ ขอเข้าคิว | เข้าคิวได้ แล้วไปเจอ "ที่นั่งเต็ม" ตอนเลือกที่นั่ง | ปฏิเสธตั้งแต่ต้นทาง พร้อมบอกว่าบัตรหมด |
| ปุ่มลงทะเบียนล่วงหน้าของรอบถัดไป | ยังกดได้ | ซ่อน (ลงทะเบียนไปก็ไม่มีบัตรให้กด) |

`SOLD_OUT` ถูกเพิ่มเป็นเหตุผลปฏิเสธตัวใหม่ใน `lib/sale-round.ts` และ**ชนะทุกเงื่อนไข** —
ไม่ว่าจะเป็นสมาชิกระดับไหน ลงทะเบียนล่วงหน้าไว้แล้วหรือมีโค้ดสิทธิ์ ก็เข้าไม่ได้ทั้งหมด

## 5. ปุ่มตั้งรอบมาตรฐาน (สมาชิกกดก่อน N วัน)

รูปแบบที่ผู้จัดใช้จริงเกือบทุกงานคือ "รอบสมาชิกก่อน 1–3 วัน แล้วต่อรอบทั่วไป" —
เดิมแอดมินต้องกรอกฟอร์ม 2 รอบ รอบละ 8 ช่อง และต้องคำนวณเวลาต่อกันเองให้ไม่ทับ/ไม่มีช่องว่าง

ตอนนี้มีปุ่มสำเร็จรูปในหน้าแอดมินคอนเสิร์ต: เลือก **เวลาเริ่มรอบสมาชิก** + **กดก่อนกี่วัน (1/2/3/7)**
\+ (ไม่บังคับ) **จำกัดตั๋วรอบสมาชิก** แล้วกด "ตั้งรอบให้เลย" → ได้ 2 รอบที่ต่อกันพอดี:

```
รอบสมาชิก  21 ส.ค. 11:46 ──► 24 ส.ค. 11:46
รอบทั่วไป                     24 ส.ค. 11:46 ──► 31 ส.ค. 11:46
```

ช่วงรอบเป็น `[start, end)` ปลายเปิด → รอบสมาชิกจบวินาทีเดียวกับที่รอบทั่วไปเริ่ม ไม่ทับกันและไม่มีช่องโหว่
ปุ่มนี้แสดงเฉพาะคอนเสิร์ตที่ยังไม่มีรอบ (กันตั้งซ้อนมั่ว) — งานที่ต้องการรอบแฟนคลับ/พาร์ทเนอร์เพิ่มยังใช้ฟอร์มเต็มได้

## 8. คิวเมื่อบัตรหมด — "ทางออก" ของคนที่รออยู่ (2026-08-26)

บั๊กที่เจอ: คอนเสิร์ตที่ไม่เหลือที่นั่ง (สร้างไว้ 0 ที่นั่ง หรือขายหมดแต่ป้าย SOLD_OUT ยังไม่ถูกติด เพราะป้ายติดเฉพาะตอนออกตั๋ว §3)
ผู้ใช้เข้าคิวได้ แล้ว **ค้าง "ตำแหน่ง 1" จน token หมดอายุ 1 ชม.** → "คิวหมดอายุ กรุณาเข้าคิวใหม่" → วนกลับมาค้างอีก

เป็นช่องโหว่ 3 จุดต่อกัน:

| จุด | เดิม | ตอนนี้ |
|---|---|---|
| ประตูเข้าคิว (`resolveEntryForUser`) | คอนเสิร์ต**ไม่มีรอบ** `return ok` ก่อนเช็คบัตรหมด — ตรรกะ §3 มีเฉพาะเส้นทางที่มีรอบ | เช็ค `getConcertAvailability` ทุกคอนเสิร์ต (ไม่มีรอบ → context เปล่า ไม่โหลดสมาชิก) · join ตอบ `action: SOLD_OUT` แยกจาก `ROUND_LOCKED` |
| ระหว่างรอ (`/api/queue/status` → `getQueueStatus`) | นับที่นั่งว่างได้ 0 → `admitNext` คืน 0 เงียบ ๆ → มีแค่ WAITING/ADMITTED/EXPIRED | ผู้ที่ได้ lock ปล่อยคิว (ทุก ~3 วิ/คอนเสิร์ต) บันทึก snapshot `{available, held}` ลง Redis `queue:{id}:seats` (TTL 30 วิ) → สถานะใหม่ **`SOLD_OUT`** เมื่อหมดจริง / `WAITING` + **`seatsFull`** เมื่อเต็มชั่วคราว — คนโพลอื่นไม่แตะ DB เพิ่ม |
| หน้าห้องรอ (`waiting-room.tsx`) | 403 ทุกแบบขึ้นจอ "ตรวจพบกิจกรรมผิดปกติ" | `SOLD_OUT` → หยุด poll + "บัตรหมดแล้ว" + ปุ่มกลับหน้าคอนเสิร์ต · `seatsFull` → "ที่นั่งทั้งหมดถูกจองไว้ชั่วคราว…" · 403 แยกตาม `action` จอบอทเฉพาะ `BLOCK` |

กติกาที่ตั้งใจ:
- **ไม่มี snapshot = ไม่รู้ = รอต่อ** — ห้ามเดาว่าหมด (โกหกว่าหมดแย่กว่าให้รอ) เช่นตอนนับที่นั่งจาก DB ไม่ได้ หรือแอดมินหยุดปล่อยคิว
- **ไม่ลบใครออกจากคิว** — snapshot หมดอายุเอง ถ้าแอดมินเปิดขายใหม่/hold หลุดกลับมา คิวไหลต่อโดยไม่ต้องเข้าคิวใหม่ · คนที่ ADMITTED แล้วไม่ถูกกระทบ (ถือที่นั่งอยู่ ให้ซื้อต่อให้จบ)
- นิยามหมดจริง/เต็มชั่วคราว (§2) ย้ายไปไฟล์ pure `lib/admit-policy.ts` แล้ว re-export จาก `lib/sold-out.ts` — `lib/queue.ts` ใช้นิยามเดียวกันโดยไม่ลาก prisma เข้าโมดูลคิว
- ทิศทางเดียว ON_SALE→SOLD_OUT ของ `syncSoldOutStatus` **ไม่เปลี่ยน** — snapshot เป็นแค่สัญญาณให้คนในคิว ไม่ใช่การประกาศสถานะคอนเสิร์ต
