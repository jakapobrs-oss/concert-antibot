## 1. ขอบเขต — สมาชิกได้อะไร (และตั้งใจไม่ให้อะไร)

| ให้ | ไม่ให้ | เหตุผล |
|---|---|---|
| เข้า **รอบสมาชิก** (`SaleRound.audience = MEMBER_ONLY`) ที่เปิดก่อนรอบทั่วไป | — | เป็นสิทธิ์เดียวของระบบนี้ |
| — | **แซงคิว** ในรอบเดียวกัน | ถ้าให้ priority แซงคิว คิวจะไม่ FIFO → สถิติ fairness/inversion ในเล่มต้องวัดใหม่ทั้งบท |
| — | **ซื้อได้มากกว่าคนทั่วไป** | ขัดกับระบบกันคนกวาดตั๋ว (named ticket + `lib/ticket-limit.ts`) ที่เป็นแกนของงานวิจัย |
| — | **ส่วนลดราคา** | ถ้าแตะราคา ต้องไปแก้ทางเดินเงิน/สลิป/คืนเงินทั้งเส้น — ความเสี่ยงไม่คุ้ม |

สรุปเป็นประโยคเดียว: **สมาชิก = "เข้าประตูก่อน" ไม่ใช่ "ได้เปรียบในห้อง"** — เข้าไปแล้วทุกคนอยู่ใต้กติกาเดิมทุกข้อ

ผลข้างเคียงที่ตั้งใจ: ระบบสมาชิก **ไม่แตะโค้ดจ่ายเงินเลยแม้แต่บรรทัดเดียว** (ตรวจได้จาก diff — ไม่มีการแก้ `lib/order-finalize.ts`, `lib/easyslip.ts`, `lib/ticket-limit.ts`)

## 2. โครงสร้างข้อมูล (สรุปจาก `prisma/schema.prisma`)

```
Membership  (1 แถวต่อ 1 user — ต่ออายุ = อัปเดตแถวเดิม)
  userId          BigInt @unique     → User (Cascade)
  status          ACTIVE | REVOKED
  source          SELF_SIGNUP | ADMIN_GRANT
  startedAt       DateTime
  expiresAt       DateTime?          -- null = ไม่มีวันหมดอายุ
  grantedByUserId BigInt?            → User (SetNull)  -- แอดมินคนที่กดให้
  revokedAt       DateTime?
  @@index([status, expiresAt])
```

**ทำไมไม่มีสถานะ `EXPIRED` ใน DB:** ถ้าเก็บเป็น status ต้องมี cron มาพลิกสถานะทุกวัน
วันไหน cron ไม่วิ่ง (deploy พลาด / เครื่องล่ม) คนที่หมดอายุแล้วจะยัง `ACTIVE` และเข้ารอบสมาชิกได้
ระบบนี้จึง **คำนวณสดทุกครั้งที่ถาม** — `active = status ACTIVE && (expiresAt = null || expiresAt > now)`
ราคาที่จ่าย: query ต้องมีเงื่อนไขวันหมดอายุติดไปด้วยเสมอ (มี index `[status, expiresAt]` รองรับ)

## 3. สัญญาฟังก์ชัน (D1 — ตกลงกับสาย SaleRound)

ทุกตัวอยู่ใน `lib/membership.ts` · `userId` รับได้ทั้ง `string` และ `bigint` · ทุกตัวรับ `now` เข้ามาได้เพื่อคุมเวลาในเทส

```ts
// ⭐ ด่านตรวจหลัก — สาย sale-round เรียกตัวนี้
isActiveMember(userId, now?): Promise<boolean>

// อยากได้รายละเอียด (เช่นเอาไปโชว์ว่าเป็นสมาชิกถึงเมื่อไร)
getActiveMembership(userId, now?): Promise<{
  id: string; userId: string;
  source: "SELF_SIGNUP" | "ADMIN_GRANT";
  tier: "STANDARD" | "PREMIUM";   // Phase 2.1 — ใช้ตัดสินสิทธิ์รอบแฟนคลับ
  startedAt: Date; expiresAt: Date | null;
} | null>          // null = ไม่ใช่สมาชิกที่ยังใช้ได้ ณ เวลา now

// ตัดสินว่า checkpoint ไหนต้องเช็คสิทธิ์ (ดู §5)
requiresActiveMembership(checkpoint): boolean
```

ตัวอย่างการใช้ฝั่ง sale-round (โค้ดที่สายนั้นจะเขียน):

```ts
import { isActiveMember, requiresActiveMembership } from "@/lib/membership";

if (round.audience === "MEMBER_ONLY" && requiresActiveMembership("ROUND_ENTRY")) {
  if (!(await isActiveMember(userId))) {
    return { ok: false, error: "รอบนี้สำหรับสมาชิกเท่านั้น" };
  }
}
```

**ข้อตกลงที่ห้ามแหก:**
1. อย่าอ่านตาราง `memberships` ตรง ๆ จากที่อื่น — ให้ผ่าน 2 ฟังก์ชันนี้เท่านั้น (เงื่อนไขวันหมดอายุจะได้อยู่ที่เดียว)
2. คอนเสิร์ตที่ **ไม่มีรอบเลย** = พฤติกรรมเดิมทุกอย่าง ห้ามเรียกเช็คสมาชิก (คอนเสิร์ตเก่าต้องไม่พัง)
3. รอบ `PUBLIC` ไม่ต้องเช็คสมาชิก (สมาชิกก็เข้าได้อยู่แล้ว)

## 4. กติกาการตัดสิน (state machine)

| สถานะที่ผู้ใช้เห็น | เงื่อนไข | สมัคร/ต่อเองได้ไหม |
|---|---|---|
| `NONE` ยังไม่เป็นสมาชิก | ไม่มีแถวใน `memberships` | ✅ ได้ |
| `ACTIVE` สมาชิก | `status=ACTIVE` และ (`expiresAt` = null หรือ > now) | ✅ ได้เมื่อเหลือ ≤ 30 วัน |
| `EXPIRED` หมดอายุ | `status=ACTIVE` แต่ `expiresAt` ≤ now | ✅ ได้ทันที |
| `REVOKED` ถูกระงับ | `status=REVOKED` | ❌ ต้องให้แอดมินคืนสิทธิ์ |

- **อายุมาตรฐาน 365 วัน** (`MEMBERSHIP_DEFAULT_DAYS`) สมัครฟรี
- **หน้าต่างต่ออายุ 30 วัน** (`MEMBERSHIP_RENEW_WINDOW_DAYS`) — สมัครฟรีและต่ออายุคือ upsert ต่อท้ายของเดิม
  ถ้าไม่มีหน้าต่างนี้ กดปุ่ม 100 ครั้ง = สิทธิ์ยาว 100 ปี
- **ต่ออายุตอนยังไม่หมด** → ต่อท้ายของเดิม (วันที่เหลือไม่หาย) · **ต่อหลังหมดแล้ว** → เริ่มนับใหม่จากวันนี้
- **ขอบเขตเวลา**: `expiresAt = now` เป๊ะ ถือว่าหมดแล้ว (ช่วงสิทธิ์เป็น `[startedAt, expiresAt)` ปลายเปิด)
- **ยืนยันตัวตนก่อนสมัคร**: ต้องยืนยันอีเมลแล้ว **หรือ** ล็อกอินผ่าน Google
  (บัญชี Google ที่ NextAuth adapter สร้างมี `emailVerified = null` จึงต้องนับ OAuth account ด้วย ไม่งั้นบล็อกผิดคน)
- **เพิกถอน ≠ ลบ**: เก็บแถวไว้พร้อม `revokedAt` เพื่อให้ตรวจย้อนหลังได้ว่าใครเคยเป็นสมาชิก

## 5. ด่านตรวจสิทธิ์ — เช็คตรงไหนบ้าง (กติกา D5)

| Checkpoint | เช็คสมาชิก | เหตุผล |
|---|---|---|
| `ROUND_ENTRY` ขอเข้ารอบ/คิวของรอบสมาชิก | ✅ | เป็นประตูจริงของสิทธิ์ |
| `ORDER_CREATE` กดจองที่นั่งสร้าง order | ✅ | กันยิง API ตรงข้ามหน้าคิว |
| `PAYMENT_CONFIRM` อัปสลิป/ยืนยันเงิน | ❌ **ไม่เช็ค** | order ที่ผ่านด่านตอนสร้างแล้ว ต้องจ่ายจบได้เสมอ |

**เคสที่กติกานี้แก้ (โจทย์ D5 "หมดอายุตอนมี order ค้าง"):**

```
12:00  สิทธิ์สมาชิกเหลืออีก 2 นาที → เข้ารอบสมาชิกได้
12:01  กดจองที่นั่ง → สร้าง order (PENDING, หมดเวลาใน 5 นาที)
12:02  สิทธิ์สมาชิกหมดอายุ
12:05  โอนเงิน + อัปสลิป
```

ถ้าเช็คสมาชิกตอน `PAYMENT_CONFIRM` ด้วย ผู้ใช้จะ **โอนเงินไปแล้วแต่ระบบไม่ออกตั๋วให้** →
กลายเป็นงานคืนเงินค้างในหน้า `/admin/refunds` ซึ่งเป็นเคสที่แย่ที่สุดของระบบเงินจริง
ระบบนี้จึงตัดสินว่า **สิทธิ์ตรวจที่ขาเข้า ไม่ตรวจย้อนหลัง** — เหมือนคิวคอนเสิร์ตจริงที่เข้าประตูไปแล้วไม่มีใครมาไล่ออกกลางทาง

ส่วน "รอบใหม่" ตอน 12:05 กดไม่ได้แล้วจริง ๆ (สิทธิ์หมดคือหมด) — เทสยืนยันทั้ง 2 ฝั่ง

## 6. หน้าจอ (D3 + D4)

### 6.1 ผู้ใช้ — `/account/membership`
- การ์ดสถานะ: ป้ายสี (สมาชิก / หมดอายุแล้ว / ถูกระงับ / ยังไม่เป็นสมาชิก) + วันเริ่ม + วันหมดอายุ + เหลืออีกกี่วัน
- ปุ่ม **สมัครสมาชิกฟรี / ต่ออายุสมาชิก** — กดแล้วมีผลทันที (ไม่ผ่าน checkout เพราะไม่มีการจ่ายเงิน)
- ถ้ายังไม่ถึงหน้าต่างต่ออายุ → บอกตรง ๆ ว่า "ต่ออายุได้เมื่อเหลือไม่เกิน 30 วัน" แทนที่จะซ่อนปุ่มเฉย ๆ
- กล่อง "สมาชิกได้อะไร" เขียนตรงกับที่ระบบทำจริง — ระบุชัดว่า **ไม่แซงคิว ไม่ได้ซื้อเยอะกว่า ไม่มีส่วนลด**
- ทางเข้า: เมนูผู้ใช้มุมขวาบน → "สมาชิก"

### 6.2 แอดมิน — `/admin/memberships`
- สรุป 3 ตัวเลข: ใช้งานได้ / หมดอายุ / ถูกเพิกถอน (นับจาก DB ตรง ๆ ไม่ใช่นับจากแถวที่ดึงมาแสดง)
- ฟอร์ม **ให้สิทธิ์ด้วยอีเมล** + เลือก 30 วัน / 90 วัน / 1 ปี / ไม่มีวันหมดอายุ
- รายชื่อ 200 รายการล่าสุด: ชื่อ-อีเมล, ป้ายสถานะ, ที่มา (สมัครเอง/แอดมินให้ + ชื่อแอดมินคนที่ให้), วันเริ่ม-หมดอายุ
- ปุ่มต่อแถว: **ต่อ 1 ปี** / **เพิกถอน** (แถวที่ถูกเพิกถอนแล้วจะเป็นปุ่ม **คืนสิทธิ์ 1 ปี**)
- ทางเข้า: แดชบอร์ดแอดมิน → ปุ่ม "สิทธิ์สมาชิก"

**ความปลอดภัยของ action แอดมิน:** ทุกตัวเรียก `assertVerifiedAdmin()` ที่ re-check `role` กับ DB จริง
(ไม่เชื่อ role ใน JWT ที่ค้างได้ถึง 30 วัน — F2 / Codex §4 #2) ซ้อนกับ middleware และ `(admin)/layout.tsx`

## 9. เนื้อหาสำหรับเล่ม (บท 3 + บท 4)

### 9.1 บทที่ 3 — การออกแบบระบบ (ส่วนสมาชิก)

**ประเด็นออกแบบที่ควรเขียนลงเล่ม 3 ข้อ:**

1. **สมาชิกเป็น "รอบเวลาแยก" ไม่ใช่ "สิทธิ์แซงคิว"**
   ทางเลือกที่ตัด: ให้ค่าถ่วงน้ำหนักสมาชิกในคิวเดียวกัน → คิวไม่เป็น FIFO → ตัวชี้วัด fairness/inversion
   ที่เป็นผลลัพธ์หลักของงานวิจัยจะใช้ไม่ได้ ต้องวัดใหม่ทั้งบท
   ทางที่เลือก: แยกช่วงเวลา (เช่น 19:00–19:30 รอบสมาชิก แล้ว 19:30 เปิดทุกคน) — ในแต่ละรอบคิวยัง FIFO เหมือนเดิม

2. **หมดอายุคำนวณสด ไม่พึ่ง cron**
   ทางเลือกที่ตัด: เก็บ `status = EXPIRED` แล้วให้ cron พลิกสถานะรายวัน → มี failure mode ที่เงียบและอันตราย
   (cron ไม่วิ่ง = คนหมดอายุยังเข้ารอบสมาชิกได้ โดยไม่มี error ให้เห็น)
   ทางที่เลือก: เก็บแค่ `expiresAt` แล้วเทียบกับเวลาปัจจุบันทุกครั้งที่ถาม — ผิดพลาดได้ยากกว่าโดยโครงสร้าง

3. **ตรวจสิทธิ์ที่ขาเข้า ไม่ตรวจย้อนหลัง**
   เหตุผลเชิงระบบเงินจริง: การตัดสิทธิ์กลางทางแปลว่า "รับเงินแล้วไม่ส่งของ" ซึ่งสร้างงานคืนเงินและความไม่ไว้ใจ
   มากกว่าประโยชน์ที่ได้จากการบังคับสิทธิ์อย่างเคร่งครัด
