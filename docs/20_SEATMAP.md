## 1. ปัญหาที่แก้

ของเดิม: ที่นั่งถูกวาดเป็น **ตารางสี่เหลี่ยม** (grid) ตายตัวต่อโซน — โซนหนึ่งคือกล่องสี่เหลี่ยมหนึ่งกล่อง

ปัญหาคือ **สถานที่จัดคอนเสิร์ตแต่ละแห่งมีพื้นที่ใช้งานไม่เหมือนกัน** — อิมแพ็คอารีน่ากับหอประชุมมหาวิทยาลัยมีรูปทรงคนละแบบ บางที่เวทีกินพื้นที่กลาง บางที่มีเสา มีทางเดิน มีอัฒจันทร์โค้ง ผังตารางสี่เหลี่ยมสื่อสารเรื่องนี้ไม่ได้เลย

คำถามที่คนซื้อต้องการคำตอบก่อนตัดสินใจจ่ายเงินมีสองข้อ:

1. **เวทีอยู่ตรงไหน**
2. **โซนที่กำลังจะซื้ออยู่ตรงไหนเมื่อเทียบกับเวที**

ผังนี้ทำหน้าที่ตอบสองข้อนี้ ไม่ได้ทำหน้าที่โชว์ที่นั่งรายตัวบนรูป

> ⚠️ ข้อจำกัดที่ยอมรับตั้งแต่ต้น: ระบบนี้ทำให้ผัง **ตรงกับรูปที่แอดมินอัปโหลด** เท่านั้น — ไม่ได้ยืนยันว่ารูปนั้นตรงกับสถานที่จริง ความถูกต้องขั้นสุดท้ายยังอยู่ที่คนกรอกข้อมูล

## 2. ทางที่พิจารณาแล้ว "ตัดทิ้ง" — อย่าเสนอซ้ำ

| ระดับ | ทำยังไง | ประเมินเวลา | ผลตัดสิน |
|---|---|---|---|
| 1. อัตโนมัติเต็มรูปแบบ | ให้คอมพิวเตอร์มองรูป (computer vision) แยกโซนออกมาเอง | 5–10 วัน | ❌ **ตัดทิ้ง** — ผังจริงมีตัวหนังสือ เส้นบอกทาง โลโก้ และใช้สีซ้ำกันคนละความหมาย เดาผิดบ่อยจนต้องแก้มืออยู่ดี |
| **2. รูปเป็นพื้นหลัง + แอดมินวาดกรอบทับ** | แอดมินคลิกวาดรูปหลายเหลี่ยม (polygon) ทับแต่ละโซนและทับเวที | 2–3 วัน | ✅ **เลือกอันนี้** |
| 3. จิ้มสีแล้วให้ระบบเดากรอบ (flood fill) | อ่านพิกเซลจาก Canvas `getImageData` | +1 วัน | 🟡 **ยังไม่ทำ** — เป็นของเสริมที่ตัดทิ้งได้ก่อนเพื่อนถ้าเวลาไม่พอ |

**เหตุผลที่เลือกระดับ 2**: มันแยก "สิ่งที่คนทำได้ดีกว่าเครื่อง" (ดูรูปแล้วรู้ว่าตรงไหนคือโซน VIP) ออกจาก "สิ่งที่เครื่องทำได้ดีกว่าคน" (จัดการข้อมูลโซนหลายสิบโซนให้ครบถ้วนสม่ำเสมอ) — แอดมินคลิก 4–6 ครั้งต่อโซน ได้ผังที่แม่นกว่าการวาดมือทั้งผัง

### 2.1 ทางที่เคยทำแล้ว "ถอดออก" (2026-08-21)

รุ่นก่อนหน้ามีอัลกอริทึม `fillPolygonWithSeats()` ที่ **โปรยจุดที่นั่งรายตัวให้เต็มกรอบ** — binary search หาระยะห่างที่นั่ง + convex hull/rotating calipers หามุมเอียงของบล็อกเพื่อหมุนกริดให้ตรงแนว + ray casting คัดจุดที่ตกในกรอบ แล้วเก็บพิกัดลง `Seat.x` / `Seat.y`

**ถอดออกทั้งชุดแล้ว** เพราะมันตอบโจทย์ที่ไม่ได้ถาม:

| สิ่งที่รุ่นเก่าทำ | ทำไมถึงถอด |
|---|---|
| คำนวณระยะห่างที่นั่งจากพื้นที่กรอบ | จำนวนบัตรมาจากตัวเลขที่ผู้จัดกำหนด ไม่ได้มาจากขนาดพื้นที่บนรูป การผูกสองอย่างนี้เข้าด้วยกันคือการสร้างความสัมพันธ์ที่ไม่มีอยู่จริง |
| หมุนกริดตามแนวบล็อก (convex hull + rotating calipers) | เกิดขึ้นเพื่อให้ "จุดที่โปรย" ดูเรียงสวยเท่านั้น — เมื่อไม่โปรยจุดแล้ว ความซับซ้อนนี้ก็ไม่มีเหตุผลรองรับ |
| เก็บพิกัด `Seat.x` / `Seat.y` | ผังระดับโซนไม่ต้องรู้ว่าที่นั่งแต่ละตัวอยู่พิกัดไหนบนรูป |
| วาดจุดหลายพันจุดทับรูป | ผังจริง 11,000 ที่นั่ง = 11,000 node ใน SVG ทำให้ผังหน่วง อ่านยาก และบังตัวหนังสือในรูป |

สิ่งที่ยังเก็บไว้จากรุ่นเก่า (ยกไปอยู่ [lib/seatmap/seat-rows.ts](../lib/seatmap/seat-rows.ts)): **ชื่อแถวฐาน 26 แบบ bijective** (A…Z แล้วขึ้น AA, AB — ไม่มีวันซ้ำในโซนเดียว) และ `compareSeatOrder()` (ลำดับอ่านผังที่แถว `AA` ต้องอยู่หลัง `Z` ไม่ใช่ระหว่าง `A` กับ `B`)

**ราคาที่จ่ายไปกับรุ่นเก่า และบทเรียน**: อัลกอริทึมนั้นถูกต้องตามที่มันตั้งใจจะทำ (เทสหน่วย 27 ข้อผ่านหมด รวมเคสบล็อกเอียง 30°) แต่ความถูกต้องของอัลกอริทึมไม่ได้แปลว่าโจทย์ถูก — **ควรถามว่า "ผู้ใช้ต้องการรู้อะไรจากผัง" ก่อนเขียนโค้ดที่แก้ปัญหาที่ยากที่สุดในหน้าจอนั้น**

## 3. Schema ที่เพิ่ม

| ตาราง | field | ชนิด | ทำไมต้องมี |
|---|---|---|---|
| `Concert` | `layoutImageBase64` | `Text?` | รูปผังสถานที่ เก็บเป็น base64 ในฐานข้อมูล |
| | `layoutImageWidth` / `layoutImageHeight` | `Int?` | ขนาดจริงของรูป — ใช้ตั้ง `viewBox` ของ SVG ให้สัดส่วนตรงกับรูปพอดี |
| | `stagePolygon` | `Json?` | **กรอบเวที** ที่แอดมินวาด — คำถามข้อแรกที่ผังต้องตอบ |
| `Zone` | `polygon` | `Json?` | กรอบโซนที่แอดมินวาด เก็บเป็น `[[x,y], ...]` |
| | `tier` | `VarChar(50)?` | **ชื่อเรทราคา** ที่โซนนี้สังกัด — ใช้จัดกลุ่มคำอธิบายสี (ดู §5.6) |
| `Seat` | `x`, `y` | `Float?` | **เลิกใช้แล้ว** — เหลือไว้เป็นคอลัมน์ว่างของข้อมูลเก่า (ดูหมายเหตุข้างล่าง) |

**ทุก field เป็น nullable ทั้งหมดโดยตั้งใจ** — คอนเสิร์ตเก่าที่มีอยู่แล้วไม่ต้องแก้อะไรเลย และยังขายบัตรได้เหมือนเดิมทุกอย่าง (ดู §6.1)

> **หมายเหตุ `Seat.x` / `Seat.y`**: ไม่มีโค้ดตรงไหนอ่านหรือเขียนแล้ว แต่ยังไม่ลบคอลัมน์ทิ้ง เพราะการลบคอลัมน์บนฐานข้อมูลที่มีข้อมูลจริงคือ migration ที่ย้อนกลับไม่ได้ และไม่มีอะไรได้กลับมานอกจากพื้นที่ไม่กี่ไบต์ — เก็บไว้เป็นหนี้ทางเทคนิคที่รู้ตัว

**ทำไมเก็บรูปเป็น base64 ในฐานข้อมูล ไม่ใช่ไฟล์แยก/S3**: ใช้แพทเทิร์นเดียวกับสลิปโอนเงิน (`Payment.slipImageUrl`) ที่ระบบนี้ใช้อยู่แล้ว — ไม่ต้องเพิ่มบริการเก็บไฟล์ใหม่ ไม่ต้องจัดการสิทธิ์เข้าถึงไฟล์อีกชุด และรูปผัง 1 รูปต่อคอนเสิร์ตมีจำนวนน้อยมาก

## 4. ข้อมูลโซนมาจากไฟล์ Excel

ผังจริงระดับอารีน่ามี **69 โซน 7 เรทราคา** การให้แอดมินกรอกชื่อ/ราคา/สี/จำนวนที่นั่งทีละโซนผ่านฟอร์มบนหน้าเว็บคือการพิมพ์ 276 ช่อง โดยที่ข้อมูลชุดนี้ผู้จัดมีอยู่ในไฟล์ Excel อยู่แล้วเสมอ

ระบบจึงอ่านไฟล์ `.xlsx` ตรง ๆ:

```
ชื่อโซน | เรทราคา | ราคา | จำนวนที่นั่ง | สี
```

| จุด | รายละเอียด |
|---|---|
| ชื่อคอลัมน์ | รับได้ทั้งไทยและอังกฤษ (`ชื่อโซน`/`zone`/`name`, `เรท`/`tier`, …) — ดู `COLUMN_ALIASES` ใน [lib/seatmap/zone-sheet.ts](../lib/seatmap/zone-sheet.ts) |
| หัวตาราง | ไม่บังคับว่าต้องอยู่แถวแรก — มองหาใน 10 แถวแรก (ไฟล์จริงมักมีโลโก้/ชื่องานอยู่ข้างบน) |
| **สี** | อ่านจาก **สีพื้นของช่อง** ในไฟล์ ไม่ใช่ข้อความ — เป็นวิธีที่คนทำผังใช้จริง (ระบายสีช่องให้ตรงกับสีในผัง) ถ้าช่องสีไม่ได้ระบายจะถอยไปอ่านสีพื้นของช่องชื่อโซนแทน และรับรหัสสีเป็นข้อความ (`#ef4444`) ได้ด้วย |
| ปุ่มดาวน์โหลดไฟล์ตัวอย่าง | `GET /api/admin/seatmap/template` สร้างไฟล์สดจากโค้ดชุดเดียวกับตัวอ่าน — ไฟล์ตัวอย่างจึงไม่มีวันล้าสมัยจากตัวอ่าน |

### กติกาที่ไฟล์ต้องผ่าน (ตรวจก่อนแตะฐานข้อมูล)

- ชื่อโซนห้ามซ้ำกันในไฟล์เดียว
- **เรทเดียวกันต้องราคาเท่ากันและสีเดียวกัน** — ถ้าไฟล์บอกว่า "เรท 1" ราคา 3,500 ที่แถวหนึ่งและ 3,800 ที่อีกแถว แปลว่าคนกรอกพิมพ์ผิด ระบบต้องบอก ไม่ใช่เดาว่าอันไหนถูก
- **เรทต่างกันต้องคนละสี** — สองเรทสีเดียวกันทำให้คำอธิบายสีบนผังโกหกคนซื้อ

**เก็บ error ให้ครบทุกแถวในรอบเดียว** ไม่ใช่หยุดที่แถวแรกที่ผิด — ไฟล์ 69 แถวที่ผิด 5 แถว ถ้าบอกทีละแถวคือให้แอดมินอัปโหลดใหม่ 5 รอบ

### ตอนนำเข้าแล้วชนกับข้อมูลเดิม

| สถานการณ์ | ระบบทำอะไร |
|---|---|
| ชื่อโซนตรงกับโซนที่มีอยู่ | อัปเดต เรท/ราคา/สี ให้ทุกครั้ง (ข้อมูลแสดงผล เปลี่ยนได้ปลอดภัย) |
| จำนวนที่นั่งในไฟล์ต่างจากในระบบ | เจนที่นั่งใหม่ — **แต่ต้องผ่านด่านกันเจนทับ (§6) ก่อน** ถ้าโซนนั้นขายบัตรไปแล้วจะถูกข้าม แล้วรายงานกลับว่าโซนไหนถูกข้ามเพราะอะไร |
| ชื่อโซนไม่มีในระบบ | สร้างโซนใหม่ + เจนที่นั่ง แต่ **ยังไม่มีกรอบ** (รอแอดมินมาวาดทับรูป) |
| โซนที่มีในระบบแต่ไม่มีในไฟล์ | **ไม่ลบ** — แค่รายงานชื่อกลับไปให้แอดมินตัดสินใจเอง (ไฟล์ที่ส่งมาไม่ครบไม่ควรลบข้อมูลที่ผูกกับเงิน) |
| โซนเดิมที่วาดกรอบไว้แล้ว | **กรอบไม่ถูกล้าง** — นำเข้าไฟล์ซ้ำไม่ทำให้ต้องวาดกรอบใหม่ทั้งผัง |

**ทำไมเขียนทีละโซนเป็นคนละ transaction ไม่ใช่ก้อนเดียว**: ผัง 69 โซน 11,000 ที่นั่งในหนึ่ง transaction จะชนเพดานเวลาของ Prisma — และการที่โซนที่ 40 ล้มไม่ควรลบล้างงานของโซนที่ 1–39 ที่สำเร็จไปแล้ว รายงานผลบอกชัดว่าโซนไหนสำเร็จ โซนไหนถูกข้าม

**ทำไมอ่านไฟล์ฝั่งเซิร์ฟเวอร์ ไม่ใช่ฝั่งเบราว์เซอร์**: ตัวอ่าน `.xlsx` ต้องใช้ API ของ Node หลายตัวที่เบราว์เซอร์ไม่มี ถ้าลากเข้า bundle ต้องเติม polyfill หลายชั้นเพื่อใช้ปีละครั้ง — แลกด้วยการที่ไฟล์ต้องเดินทางผ่าน server action จึงคุมด้วย: เช็คสิทธิ์แอดมินก่อน · จำกัดขนาดไฟล์ · จำกัดจำนวนแถว (500) และจำนวนที่นั่งต่อโซน (5,000) · ตรวจซ้ำด้วย zod ก่อนลงฐานข้อมูล

## 5. การตัดสินใจที่มีผลกับความถูกต้อง

### 5.1 พิกัดเก็บเป็นสัดส่วน 0–1 ไม่ใช่พิกเซล

ถ้าเก็บเป็นพิกเซล ผังจะเพี้ยนทันทีเมื่อเปิดคนละหน้าจอ หรือเมื่อแอดมินอัปโหลดรูปใหม่ที่ความละเอียดต่างเดิม — เก็บเป็นสัดส่วนแล้วคูณกลับตอนวาด ทำให้ผังถูกต้องทุกขนาดหน้าจอ

### 5.2 จำนวนที่นั่งไม่ผูกกับขนาดกรอบ

วาดกรอบเล็กแล้วสั่ง 500 ที่ ก็ได้ 500 ที่ — เพราะ **จำนวนบัตรเป็นเรื่องที่ผู้จัดกำหนด ไม่ใช่เรื่องที่คำนวณจากรูป** การจับสองอย่างนี้มาผูกกันคือการสร้างข้อผูกมัดที่ไม่มีในโลกจริง และทำให้แอดมินต้องมาวาดกรอบใหม่เพียงเพราะอยากเพิ่มบัตรอีก 20 ใบ

ที่นั่งถูกจัดเป็นแถวด้วย [lib/seatmap/seat-rows.ts](../lib/seatmap/seat-rows.ts) — จำนวนที่นั่งต่อแถวคิดจาก `√(จำนวน × 2)` แล้วบีบให้อยู่ระหว่าง 8–40 ที่ต่อแถว ทำให้โซน 40 ที่ได้ประมาณ 9 ที่ต่อแถว และโซน 2,000 ที่ได้ 40 ที่ต่อแถว ซึ่งใกล้เคียงสัดส่วนของโรงมหรสพจริงโดยไม่ต้องให้แอดมินกรอกเพิ่ม

### 5.3 สร้าง component ใหม่ ไม่แก้ของเดิม

`components/seat-map.tsx` (ผังตารางแบบเดิม) คือทางเดินเงินที่ผ่านการทดสอบมาแล้ว — การไปแก้มันเพื่อรองรับผังรูปคือการเอาความเสี่ยงไปวางบนโค้ดที่ทำงานถูกอยู่แล้ว

จึงสร้าง `components/seat-map-svg.tsx` แยกต่างหาก แล้วให้หน้าเลือกที่นั่งสลับเอาตามข้อมูลที่มี ผลคือ **คอนเสิร์ตเก่าเดินโค้ดเส้นเดิมทุกบรรทัด ไม่มีทางพังจากฟีเจอร์นี้**

ต้นทุนที่ยอมจ่าย: โค้ดส่วนส่งฟอร์มซ้ำกันสองที่ (เขียนบอกไว้ในหัวไฟล์แล้ว) — ยอมแลกเพื่อไม่ต้องแตะทางเดินเงิน

### 5.4 สลับผังแบบ "ครบทุกชิ้นเท่านั้น" (all-or-nothing)

หน้าเลือกที่นั่งใช้ผังรูปต่อเมื่อ **ครบทุกเงื่อนไข**: มีรูป + มีขนาดรูป + **ทุกโซน**มีกรอบที่อ่านได้ + ทุกโซนมีที่นั่ง ขาดชิ้นใดชิ้นหนึ่งถอยไปใช้ผังตารางเดิม **ทั้งหน้า**

เหตุผล: ทางเลือกอีกแบบคือสลับ "ทีละโซน" ซึ่งจะได้หน้าจอที่มีผังรูปครึ่งหนึ่ง ตารางครึ่งหนึ่ง — คนซื้อจะอ่านไม่ออกว่ากำลังดูอะไร ระหว่าง "ผังไม่สวยแต่ใช้ได้" กับ "ผังสับสน" เลือกอย่างแรก

**กรอบเวทีไม่อยู่ในเงื่อนไขนี้** — ผังยังอ่านออกถ้ายังไม่ได้ระบุเวที แค่ไม่มีป้ายเวทีและเรียงโซนตามราคาแทนระยะจากเวที

การอ่านกรอบจากฐานข้อมูลผ่าน `parsePolygon()` ([lib/seatmap/polygon.ts](../lib/seatmap/polygon.ts)) ซึ่งตรวจรูปร่างจริงและคืน `null` เมื่อข้อมูลผิดรูป (แก้มือในฐานข้อมูล ของเก่าคนละเวอร์ชัน ตัวเลขเป็น `NaN`) — ผลคือหน้าเว็บถอยไปผังตาราง แทนที่จะพังตอนวาด

### 5.5 ทางแยกสำหรับโซนที่ขายบัตรไปแล้ว — `assignZoneFrame`

ด่านกันเจนทับ (§6) ปฏิเสธการเจนที่นั่งใหม่ทับโซนที่มีที่นั่งขายแล้วอย่างถาวร ซึ่ง **ถูกต้อง** เพราะ "เจนใหม่" = ลบที่นั่งเดิมทิ้งแล้วสร้างใหม่

แต่ผลข้างเคียงคือ: คอนเสิร์ตที่กำลังขายอยู่จะไม่มีวันได้ผังบนรูปจริงเลย — ติดตายทั้งที่สิ่งที่ต้องการแค่ "วาดกรอบทับรูป"

จึงมี `assignZoneFrame()` ที่เขียน **เฉพาะ `Zone.polygon`** ไม่แตะตาราง `seats` เลยแม้แต่แถวเดียว — `id`, `rowLabel`, `seatNumber`, `status` ของที่นั่งทุกตัวยังเป็นค่าเดิม ตั๋วที่ลูกค้าถืออยู่จึงยังชี้ที่นั่งเดิมทุกใบ

> ในรุ่นเก่าทางนี้ต้องยิง `UPDATE ... FROM (VALUES ...)` ย้ายพิกัดที่นั่งทั้งโซน และต้องระวังลำดับการจับคู่ให้ตรงกันเป๊ะ — พอที่นั่งไม่มีพิกัดแล้ว ความเสี่ยงทั้งก้อนนั้นก็หายไป เหลือแค่ `UPDATE zones SET polygon = ...` แถวเดียว

### 5.6 คำอธิบายสีจัดกลุ่มตาม "เรท" ไม่ใช่ตามโซน

ผังอิมแพ็คมี 69 โซนแต่มีแค่ 7 เรทราคา ถ้าไล่แสดงทีละโซนจะได้คำอธิบายสี 69 บรรทัด ทั้งที่สีซ้ำกันหมด — จัดกลุ่มตาม `tier` แล้วแสดง 7 บรรทัดพร้อมจำนวนโซนและจำนวนที่นั่งรวมของเรทนั้น ตรงกับที่ผังขายบัตรจริงพิมพ์ไว้

## 6. ด่านความปลอดภัย

### 6.1 กันเจนที่นั่งทับของที่มีภาระผูกพัน

[lib/seatmap/guard.ts](../lib/seatmap/guard.ts) — `canRegenerateZoneSeats()` เขียนเป็นฟังก์ชันบริสุทธิ์ (รับสภาพที่นั่ง คืนคำตัดสิน) เพื่อให้ทดสอบตรรกะตรง ๆ ได้โดยไม่ต้องมีฐานข้อมูล

ปฏิเสธเมื่อพบที่นั่งที่:

| เงื่อนไข | ทำไมถึงห้าม |
|---|---|
| `SOLD` | ตั๋วที่จ่ายเงินจริงแล้วจะชี้ไปยังที่นั่งที่ไม่มีอยู่ |
| `HELD` | มีคนกำลังอยู่หน้าจ่ายเงิน ลบไปคือตัดกลางคัน |
| ยังมีตั๋วผูกอยู่ (รวมตั๋วที่คืนแล้ว) | ลบที่นั่งจะชน foreign key |
| ยังมี order item ผูกอยู่ | เหตุผลเดียวกัน |

`BLOCKED` (แอดมินปิดที่นั่งเอง) **ไม่ใช่** ภาระผูกพัน — เจนทับได้ แต่สถานะที่ปิดไว้จะหายไปด้วย

**ด่านนี้บังคับใช้กับการนำเข้า Excel ด้วย** ไม่ใช่แค่ฟอร์มบนหน้าเว็บ — ไฟล์ที่บอกว่าโซน VIP มี 500 ที่ (จากเดิม 480) จะไม่ทำให้ที่นั่งที่ขายไปแล้วหายไป ระบบข้ามโซนนั้นแล้วรายงานกลับ

### 6.2 🔴 จุดที่ตรวจฐานข้อมูลอย่างเดียวแล้วพลาด

ระบบนี้จองที่นั่งด้วยการล็อกใน Redis (`seat:lock:{seatId}`) ก่อน — **`Seat.status` ในฐานข้อมูลจะกลายเป็น `HELD` ตอนยืนยันคำสั่งซื้อเท่านั้น**

แปลว่าช่วงที่ลูกค้ากำลังกรอกข้อมูลอยู่หน้าจ่ายเงิน ฐานข้อมูลยังบอกว่า `AVAILABLE` อยู่ ถ้าด่านดูแค่ฐานข้อมูลก็จะอนุญาตให้เจนทับ → **ลบที่นั่งออกจากใต้เท้าคนที่กำลังจะจ่ายเงิน**

ด่านจึงต้องถาม Redis ด้วย (`getHeldSeats()`) แล้วนับเป็น `HELD` — มีเทสยืนยันเงื่อนไขนี้ตรง ๆ (ยืนยันก่อนว่าฐานข้อมูลเป็น `AVAILABLE` จริงขณะที่ Redis ล็อกอยู่ แล้วจึงยืนยันว่าถูกปฏิเสธ)

### 6.3 ด่านทั่วไป

- ทุก action เรียก `assertVerifiedAdmin()` ก่อนเสมอ · route ดาวน์โหลดไฟล์ตัวอย่างเรียก `isVerifiedAdmin()` (เช็ค role กับฐานข้อมูลจริง ไม่เชื่อ JWT ค้าง)
- ตรวจ input ด้วย zod ทุกตัว: กรอบต้องมี 3–60 จุด, จำนวนที่นั่งต่อโซนไม่เกิน 5,000, รูปต้องเป็นรูปจริง, ชื่อเรทไม่เกิน 50 ตัวอักษร
- จำกัดขนาด base64 ของรูปที่ 2.8 ล้านตัวอักษร (≈ 2MB) และของไฟล์ Excel ที่ 1.4 ล้านตัวอักษร (≈ 1MB) ให้ต่ำกว่าเพดาน request ของ Server Actions ที่ตั้งไว้ 3MB
- ย่อรูปฝั่งเบราว์เซอร์ก่อนส่ง (กว้าง 1600px → webp) เพราะผังจริงมักโดด 3–4MB
- ตรวจว่าโซนอยู่ในคอนเสิร์ตที่อ้างจริง กันการยิงข้ามคอนเสิร์ต

## 7. Flow การใช้งาน

### แอดมิน

```
1. อัปโหลดรูปผังสถานที่               -> เห็นรูปเป็นพื้นหลังทันที
2. ดาวน์โหลดไฟล์ตัวอย่าง -> กรอกข้อมูลโซนทั้งงานใน Excel -> นำเข้า
                                      -> ได้โซนครบทุกโซน พร้อมเรท/ราคา/สี/ที่นั่ง
3. กด "วาดกรอบเวที" -> คลิก 4 จุดทับเวทีในรูป -> บันทึก
4. กด "วาดกรอบโซน" -> คลิก 4-6 จุดทับโซน -> กด "ตั้งกรอบให้โซนนี้"
5. ทำซ้ำข้อ 4 จนครบทุกโซน
```

โซนที่ขายบัตรไปแล้วจะเห็นป้าย "ขายแล้ว N" / "จองค้าง N" และปุ่มเจนที่นั่งใหม่จะถูกปฏิเสธ — ใช้ **"ตั้งกรอบให้โซนนี้"** ซึ่งไม่แตะที่นั่งเลย (§5.5)

### คนซื้อ

เข้าหน้าเลือกที่นั่งตามปกติ (ต้องผ่านคิวก่อนเหมือนเดิม) — ถ้าคอนเสิร์ตนั้นทำผังไว้ครบจะเห็นผังบนรูปจริง:

- **เวทีมีป้ายกำกับบนผัง** และรายการโซนเรียงจาก "ใกล้เวทีที่สุด" (วัดจากจุดศูนย์ถ่วงของกรอบโซนถึงจุดศูนย์ถ่วงของกรอบเวที) — ถ้ายังไม่ได้ระบุเวทีจะเรียงตามราคาแทน
- **แตะโซนบนผัง (หรือเลือกจากรายการโซน) → เปิดแผงเลือกที่นั่งของโซนนั้น** ที่นั่งจัดเป็นแถวมีตัวอักษรแถวกำกับ
- **โซนที่เต็มแล้วเป็นสีเทาและกดไม่ได้** — ไม่ต้องเปิดเข้าไปดูถึงจะรู้
- **คำอธิบายสีจัดกลุ่มตามเรทราคา** (§5.6)
- **ซูมได้ 3 ระดับ** สำหรับผังที่มีโซนย่อยหลายสิบโซน

ส่วนที่เหลือ (กดเลือก → จองที่นั่ง → ไปหน้าจ่ายเงิน) เดินทางเดิมทุกขั้น

### ♿ ผลพลอยได้ด้านการเข้าถึง

รุ่นก่อนวาดที่นั่งเป็น `<circle>` ใน SVG พร้อม `onClick` — **กดด้วยคีย์บอร์ดไม่ได้เลยทั้งผัง และโปรแกรมอ่านหน้าจอไม่เห็นที่นั่งสักที่**

รุ่นนี้แผงเลือกที่นั่งเป็น `<button>` จริงใน HTML ที่มี `aria-label` บอกโซน/แถว/เลขที่นั่ง และ `aria-pressed` บอกว่าเลือกอยู่ไหม — ผู้ใช้คีย์บอร์ดกด Tab เข้าถึงได้ทุกที่นั่ง และรายการโซนก็เป็นปุ่มจริงเช่นกัน จึงมีทางเลือกโซนที่ไม่ต้องพึ่งการคลิกบนรูป

### สิ่งที่เทสพิสูจน์ (เลือกข้อที่มีน้ำหนัก)

**การอ่านไฟล์ Excel**
- อ่านไฟล์ `.xlsx` จริงได้ครบวงจร — สร้างไฟล์ตัวอย่างจากโค้ดจริงแล้ววนกลับมาอ่านด้วยตัวอ่านจริง ไม่ได้ mock ชั้นไหนเลย
- อ่านสีจาก **สีพื้นของช่อง** ได้จริง และถอยไปอ่านช่องชื่อโซนเมื่อช่องสีว่าง
- หัวตารางที่ไม่ได้อยู่แถวแรกก็หาเจอ · ชื่อคอลัมน์ไทย/อังกฤษใช้ได้ทั้งคู่
- **เรทเดียวกันราคาไม่ตรงกัน → ปฏิเสธ** · **เรทต่างกันใช้สีเดียวกัน → ปฏิเสธ** · ชื่อโซนซ้ำ → ปฏิเสธ
- ไฟล์ที่ผิดหลายแถวรายงาน **ครบทุกแถวในรอบเดียว** พร้อมเลขแถว

**การจัดแถวที่นั่ง**
- สั่งกี่ที่ได้เท่านั้นเป๊ะทุกจำนวน — และ **จำนวนไม่เปลี่ยนตามขนาดกรอบ** (ยืนยันในเทสรวม: ตั้งกรอบใหม่ที่เล็กลงมาก จำนวนที่นั่งยังเท่าเดิม)
- แถวเกิน 26 แถวใช้ชื่อ AA, AB ต่อ ไม่ชนกับ A · ไม่มีแถว/เลขที่นั่งซ้ำกัน
- `compareSeatOrder` เรียง `AA` ไว้หลัง `Z` ไม่ใช่ระหว่าง `A` กับ `B`

**ด่านความปลอดภัย (จุดที่แตะเงินจริง)**
- มีที่นั่ง `SOLD` แม้แค่ที่เดียว → ปฏิเสธ และที่นั่งเดิมยังอยู่ครบไม่ถูกลบ
- มีล็อกค้างใน Redis ขณะที่ฐานข้อมูลยังเป็น `AVAILABLE` → ปฏิเสธ (เทสยืนยันเงื่อนไขนี้ก่อนแล้วจึงทดสอบ)
- ยังมีตั๋วผูกอยู่แม้สถานะว่างแล้ว → ปฏิเสธ (กันชน foreign key)
- เคลียร์ภาระผูกพันหมดแล้ว → เจนทับได้

**`assignZoneFrame` บนโซนที่ขายบัตรไปแล้ว**
- ตั้งกรอบใหม่สำเร็จแม้โซนมีที่นั่ง `SOLD`
- **`id` ที่นั่งทุกตัวเป็นตัวเดิม** ไม่มีการลบแล้วสร้างใหม่ (เทียบด้วย `id` ไม่ใช่แค่จำนวน)
- ชื่อแถว/เลขที่นั่งไม่เปลี่ยน · ที่นั่งที่ขายแล้วยังเป็น `SOLD` · `totalSeats` ไม่ถูกแตะ

**การนำเข้าไฟล์ผ่านหน้าจอจริง**
- โซนเดิมถูกอัปเดต ไม่ถูกสร้างซ้ำ · **กรอบที่วาดไว้แล้วไม่ถูกล้างทิ้ง**
- โซนใหม่จากไฟล์ถูกสร้างพร้อมที่นั่งครบ และ **ยังไม่มีกรอบ** (สถานะที่ถูกต้อง — รอแอดมินมาวาด)

**ฝั่งคนซื้อ**
- คอนเสิร์ตที่ทำผังครบ → เห็นกรอบโซนและกรอบเวทีบนรูป และ **ไม่มีจุดที่นั่งรายตัวหลงเหลือ**
- ยังไม่เลือกโซน → ยังไม่มีปุ่มที่นั่งให้กด · แตะโซนบนผัง → เปิดแผงเลือกที่นั่งครบทุกที่
- ที่นั่งเป็นปุ่มที่มีชื่อให้โปรแกรมอ่านหน้าจอจริง (ค้นด้วย accessible name ได้)
- ลบกรอบโซนออก → ถอยไปผังตารางเดิมได้จริง (ทดสอบก่อนสร้างคำสั่งซื้อ เพื่อไม่ให้เปลืองสิทธิ์ซื้อ)
- กดเลือกที่นั่งจริงแล้วไปถึงหน้าจ่ายเงิน — ตรวจทั้งรายการในคำสั่งซื้อ และล็อกที่เกิดขึ้นจริงใน Redis

### สองเรื่องที่ตั้งใจทำต่างจากปกติ

**1. เทสไฟล์ Excel ใช้ไฟล์จริง ไม่ mock ตัวอ่าน**
เทสหน่วยของ `zone-sheet` สร้างไฟล์ `.xlsx` ด้วย exceljs จริง (รวมการระบายสีพื้นช่อง) แล้วอ่านกลับด้วยตัวอ่านของระบบ — ถ้า mock ชั้นอ่านไฟล์ จะพิสูจน์ได้แค่ว่าตัว validator ทำงาน ไม่ได้พิสูจน์ว่าอ่านสีจากไฟล์จริงออก

**2. เทสฝั่งคนซื้อไม่เดินผ่านหน้าห้องรอ**
หน้าห้องรอมี Cloudflare Turnstile ของจริงทำงานอยู่ — การไปแก้หรือข้าม CAPTCHA คือสิ่งที่ระบบนี้ทั้งระบบสร้างมาเพื่อกัน เทสจึงเตรียมบัตรผ่านคิวด้วยการเรียก `joinQueue()` / `admitNext()` ของระบบเอง แล้วเริ่มทดสอบที่หน้าเลือกที่นั่ง (เขียนบอกไว้ในหัวไฟล์เทสแล้ว)

## 8.2 งานรอบ 2026-08-24 — โซนยืน · ระบบเลือกที่นั่งให้ · แถวยาวไม่เท่ากัน (branch `feat/seatmap`)

ทำ 3 ขั้นตามแผน `HANDOFF-zone-seat-layout.md` — ตรวจรับบนเว็บจริง + ฐานข้อมูลจริงครบทุกขั้นแล้ว

**ขั้น 1 — โซนยืน (`Zone.isStanding`)**: โซนยืนขายเป็น "จำนวนใบ" ไม่มีผังแถว — ฝั่งคนซื้อเปิดแผงเลือกจำนวนแทนกริดที่นั่ง, action ใหม่ `holdStandingZone` สุ่มหยิบที่นั่งว่าง (oversample 3 เท่า, retry ≤3 กันชนกันตอนแย่งพร้อมกัน) แล้วส่งเข้า `holdAndCreateOrder` เดิม — ไส้เงินไม่ถูกแตะ. Excel มีคอลัมน์ "ประเภทโซน" (ยืน/นั่ง). โซนยืนห้ามมี rowSpec.

**ขั้น 2 — ระบบเลือกที่นั่งให้ (best-available) + ปิดรูรั่วข้อมูลที่นั่ง (§0.4)**:
- โหมด "ระบบเลือกให้" เป็นค่าเริ่มต้นของโซนนั่ง: `holdBestAvailable` ดึงที่นั่งว่างเรียง **แถวหน้าสุด → ที่ติดกันก่อน** (`pickBestSeats` หาช่วง seatNumber ติดกันยาวพอในแถวหน้าสุด, ไม่มีก็ถอยเป็นเรียงลำดับ), retry ≤3 ตัดที่นั่งที่ hold พลาดออกจากรอบถัดไป
- ⚠️ บั๊กที่เจอตอนตรวจรับ: ORDER BY `rowLabel` แบบ string ทำ `AA` แทรกระหว่าง `A` กับ `B` → โซน >26 แถวที่ว่างเกิน 500 ที่ แถวหน้าหลุดจากหน้าต่าง candidate → แก้เป็น `ORDER BY LENGTH("rowLabel"), "rowLabel", "seatNumber"` (กติกาเดียวกับ `compareSeatOrder`)
- **ปิดรูรั่ว**: หน้าเลือกที่นั่งเลิกส่งผังที่นั่งทุกโซนมากับ payload แรก (บอทเคยกวาดได้ทั้งผังโดยไม่กดอะไร) — ตอนนี้ส่งแค่ `availability {ว่าง, ทั้งหมด}` ต่อโซน แล้วค่อยโหลดรายโซนผ่าน `GET /api/concerts/[id]/zones/[zoneId]/seats?qt=` เมื่อผู้ใช้กดโหมดเลือกเอง — ด่านครบ: ต้อง login + ผ่านคิว (`isAdmitted`) + rate limit 30 ครั้ง/นาที/คน/คอนเสิร์ต (sliding window เดิมของ Phase 6). ทางถอยผังตารางเดิม (`seat-map.tsx`) ไม่แตะ จึงยังส่งเต็มเหมือนเดิม — ยอมรับไว้เพราะใช้กับคอนเสิร์ตที่ไม่มีผังรูปเท่านั้น

**ขั้น 3 — แถวยาวไม่เท่ากัน (`Zone.rowSpec`)**: ผังจริงแถวหน้าสั้นแถวหลังยาว — เก็บเป็น JSON array จำนวนที่ต่อแถว เช่น `"[12,14,16]"` (null = จัดอัตโนมัติแบบเดิม), **invariant: ผลรวมต้องเท่า `totalSeats` เสมอ** ไม่ตรง = error ชัดเจน ไม่ปรับให้เงียบ ๆ
- แอดมิน: ปุ่ม "จัดแถว" ต่อโซนนั่ง → แผงแก้จำนวนรายแถว (ค่าตั้งต้นอ่านจากผังจริง, โชว์ "รวม X / ต้องได้ Y" สด, ผลรวมไม่ตรง = ปุ่มบันทึก disabled) → action `saveZoneRowSpec` · ฟอร์มโซนใหม่ + คอลัมน์ Excel "ที่นั่งต่อแถว" (`12,14,16`) เข้าทางเดียวกัน
- ทุกทางที่ลบ/เจนที่นั่งใหม่รวมศูนย์ผ่าน `regenerationVerdict()` (เช็คภาระผูกพันใน DB + ล็อกสดใน Redis) — ไล่ทุก call-site แล้วไม่มีทางหลุด
- ฝั่งคนซื้อไม่ต้องแก้ — กริดวาดจากที่นั่งจริงต่อแถวอยู่แล้ว (ตรวจบนเว็บจริง: แถว 10/28/19/9 แสดงตรงตาม spec)
