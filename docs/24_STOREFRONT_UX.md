> รอบนี้ไม่ได้เพิ่มกลไกใหม่เชิงระบบ แต่ปิด **ช่องโหว่ด้าน UX 3 จุด** ที่เว็บกดบัตรจริงทุกเจ้ามี

## 1. ทำไมต้องมี 3 อย่างนี้

| ฟีเจอร์ | ปัญหาจริงที่แก้ | ถ้าไม่มีจะเกิดอะไร |
|---|---|---|
| **คำสั่งซื้อของฉัน** (`/account/orders`) | order ที่ยังไม่จ่าย (อายุ 5 นาที) **ไม่มีทางกลับเข้าไปจ่ายต่อ** ถ้าปิดแท็บ checkout | ผู้ใช้เสียที่นั่งทั้งที่เงินยังไม่ตัด · ทีมงานตอบไม่ได้ว่า order อยู่ไหน · ที่นั่งค้าง HELD 5 นาทีโดยไม่มีใครกลับมาซื้อ |
| **นับถอยหลังเปิดขาย/เปิดรอบ** | ผู้ใช้ไม่รู้ว่าเหลืออีกกี่วินาที ต้องเดาแล้วกด F5 | กดรีเฟรชรัวก่อนเปิดขาย = โหลดพุ่งตอนที่ระบบเปราะที่สุด · คนที่รีเฟรชถี่กว่าได้เปรียบ = ไม่เป็นธรรม |
| **ค้นหา/กรองรายการงาน** | รายการงานเป็นลิสต์ยาวเรียงเดียว ไม่มีค้นหา | พองานเกิน 10 รายการหาไม่เจอ · คนจำชื่อทัวร์เต็มไม่ได้แต่จำสนามได้ |

## 2. คำสั่งซื้อของฉัน

**สถานะคำนวณสดจากเวลา** (`lib/order-view.ts`) — ไม่รอ sweeper มาปิด order ก่อนถึงจะแสดงถูก
(แพทเทิร์นเดียวกับสมาชิก/รอบขาย: อะไรที่ขึ้นกับเวลา ให้คำนวณตอนอ่าน ไม่ต้องมี cron)

| สถานะที่ผู้ใช้เห็น | เงื่อนไข | ทำอะไรต่อได้ |
|---|---|---|
| **รอชำระเงิน** | `PENDING` และยังไม่หมดเวลา | ปุ่ม **จ่ายเงินต่อ** (กลับเข้า `/checkout/[id]`) + **ยกเลิก** + นับถอยหลังเวลาที่เหลือ |
| **หมดเวลาชำระ** | `PENDING` แต่เลย `expiresAt` | ลิงก์ไปจองใหม่ |
| **ชำระแล้ว** | `PAID` | ลิงก์ไปดูตั๋ว |
| **ยกเลิกแล้ว** | `CANCELLED` | — |
| **รอทีมงานคืนเงิน** | `Payment.status = REFUND_REQUIRED` | ข้อความอธิบายว่าเงินเข้าแล้วแต่ออกตั๋วไม่ได้ ทีมงานกำลังคืนเงิน |

🔑 **"รอทีมงานคืนเงิน" ชนะสถานะ order เสมอ** — เคสเงินเข้าแต่ออกตั๋วไม่ได้ (Codex #3) order จะเป็น `CANCELLED`
ถ้าโชว์ตามสถานะ order ผู้ใช้จะเห็นแค่ "ยกเลิกแล้ว" ทั้งที่จ่ายเงินไปแล้ว — เป็นเคสที่ผู้ใช้โกรธที่สุด

**ปุ่มยกเลิกมีประโยชน์กับระบบด้วย:** ยกเลิกเอง = ที่นั่งกลับเข้าระบบทันที ไม่ต้องรอครบ 5 นาที
ตอนบัตรใกล้หมด ที่นั่งหมุนกลับมาขายเร็วขึ้นหลายเท่า

## 3. นับถอยหลัง (`lib/countdown.ts` + `components/countdown.tsx`)

ใช้ 2 จุด: หน้าคอนเสิร์ตที่ยังไม่เปิดขาย และการ์ดรอบที่ยังไม่เริ่มในแผงรอบกดบัตร

**หลักการที่ยึด:**
1. **เวลาเป้าหมายมาจาก server เสมอ** (ISO string) — ตัวนับเป็นแค่ตัวช่วยสายตา
2. **ห้ามปลดล็อกปุ่มเองจากนาฬิกาเครื่องผู้ใช้** — พอนับถึงศูนย์ ตัวนับจะ **ยิงถาม server ครั้งเดียว**
   (`onReach` → refetch) แล้วให้ server เป็นคนบอกว่าเปิดจริงหรือยัง
   ⇒ นาฬิกาเครื่องเร็ว/ช้าไม่ทำให้ใครได้เปรียบ และไม่มีใครกด F5 รัวอีก
3. **ความถี่ tick ปรับตามเวลาที่เหลือ** — เหลือเกิน 1 วันเต้นนาทีละครั้ง (หน้าเปิดค้างทั้งวันไม่กิน CPU)
4. **ข้อความอ่านง่ายตามระยะ** — `2 วัน 3 ชม.` / `1:05:05 ชม.` / `4:09 นาที` (ไม่ใช่ 51:23:07 ที่อ่านยาก)

## 4. ค้นหา/กรองงาน (`lib/concert-filter.ts` + `components/concert-browser.tsx`)

- ค้นได้ทั้ง **ชื่องานและสถานที่** — คนจำ "อิมแพ็ค" ได้แต่จำชื่อทัวร์เต็มไม่ได้ เป็นเรื่องปกติ
- แท็บกรอง: ทั้งหมด / กำลังขาย / เร็ว ๆ นี้ / บัตรหมด **พร้อมตัวเลขจำนวนงานในแต่ละหมวด**
- **กรองฝั่ง client ล้วน** — หน้ารายการเป็นหน้าแคช (`revalidate 60`) และงานที่เปิดขายมีหลักสิบ
  ⇒ พิมพ์แล้วผลขึ้นทันทีโดยไม่ยิงเซิร์ฟเวอร์เพิ่มสักครั้ง (สำคัญมากในวันเปิดขายที่คนแห่เข้าเว็บ)

## 6. ที่ยังไม่ทำ

| ไม่ทำ | เหตุผล |
|---|---|
| อีเมลยืนยันคำสั่งซื้อ / เตือนก่อนหมดเวลาจ่าย | มี `lib/email.ts` (Resend) แต่ยังไม่มีคิวงาน — และโควต้าอีเมลฟรีมีจำกัด |
| แจ้งเตือน "เปิดขายแล้ว" (push/อีเมล) | ต้องมีระบบ subscription ของ notification แยก |
| กรองตามช่วงราคา/วันที่/ประเภทงาน | ตอนนี้ยังมีงานหลักหน่วย — เพิ่มตัวกรองเกินจำเป็น (`filterConcerts` รับพารามิเตอร์เพิ่มได้ทันทีเมื่อถึงเวลา) |
| แบ่งหน้า (pagination) ของรายการงาน | ยังไม่จำเป็นที่จำนวนงานระดับนี้ |
