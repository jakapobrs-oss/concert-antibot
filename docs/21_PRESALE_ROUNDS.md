# 21 — รอบพรีเซลหลายชั้น (Presale Rounds) ตามแพลตฟอร์มจริง

> สถานะ: **โค้ดเสร็จ + ทดสอบบนเครื่องจริงแล้ว** · เขียน 2026-08-20
> ต่อยอดจาก [20_MEMBERSHIP.md](20_MEMBERSHIP.md) — ไฟล์นั้นคือ "ใครเป็นสมาชิก", ไฟล์นี้คือ "สมาชิกใช้สิทธิ์ตอนไหน"
> ที่มา: คู่มือการซื้อบัตรรอบพรีเซลด้วยระบบสมาชิกในไทย (Live Nation Tero, Weverse, ALPHAZ, The Concert App, All Ticket, พรีเซลบัตรเครดิต)

---

## 1. แมปของจริง → ระบบนี้

| กลไกในแพลตฟอร์มจริง | ทำในระบบนี้ยังไง | สถานะ |
|---|---|---|
| ลำดับรอบพรีเซล 4 ชั้น (แฟนคลับ → สปอนเซอร์ → ผู้จัด → ทั่วไป) | `SaleRoundAudience` = `FANCLUB` / `PARTNER` / `MEMBER_ONLY` / `PUBLIC` | ✅ |
| ระดับสมาชิก (ALPHAZ: พรีเมียม/มาตรฐาน — ระดับสูงเข้าก่อน) | `Membership.tier` = `PREMIUM` / `STANDARD` | ✅ |
| ลงทะเบียนล่วงหน้า (Weverse: เป็นสมาชิกอย่างเดียวไม่พอ ต้องกดในช่วงที่ประกาศ) | `SaleRound.requiresPreRegistration` + ตาราง `PreRegistration` + หน้าต่างเวลา | ✅ |
| โค้ดสปอนเซอร์ / พรีเซลบัตรเครดิต / รหัสจากใบเสร็จ | ตาราง `AccessCode` + `AccessCodeRedemption` | ✅ |
| โควต้าที่นั่งที่ล็อกไว้ให้รอบ (แฟนคลับได้โซนหน้าก่อน) | `SaleRound.seatQuota` (บังคับใน transaction เดียวกับที่จองที่นั่ง) | ✅ |
| เพดานตั๋วรอบพรีเซลตึงกว่ารอบปกติ (มัก 2 ใบ) | `SaleRound.maxTicketsPerUser` (ใช้ค่าที่ตึงกว่าเสมอ) | ✅ |
| ชื่อบนบัตรต้องตรงกับตัวตน (กันปัญหาหน้าประตู) | มีอยู่แล้ว — named ticket + เช็คอินเทียบบัตรประชาชน ([19](19_NAMED_TICKET_PLAN.md)) | ✅ เดิม |
| ยืนยันตัวตนด้วย OTP มือถือ | ใช้ยืนยันอีเมล/Google แทน (SMS มีค่าใช้จ่ายต่อข้อความ) | ⚪ ทดแทน |
| สมาชิกรายปีแบบเสียเงิน (Weverse ~600–700 บาท/ปี) | **ตั้งใจไม่ทำ** — จะลากทางเดินเงิน/สลิป/คืนเงินทั้งเส้นเข้ามาโดยไม่เพิ่มค่าเชิงวิจัย | ❌ ตัดออก |

**สิ่งที่ยืมมาแต่ไม่ลอกทั้งดุ้น:** ของจริงหลายเจ้าใช้ "ลำดับคิว" (queue priority) ปนกับ "ลำดับรอบ"
ระบบนี้เลือกทำเฉพาะ **ลำดับของรอบเวลา** เท่านั้น — ในทุกรอบ คิวยังจัดด้วย time-bucket + สุ่มเหมือนเดิม
ทำแบบนี้เพราะถ้าให้สมาชิกแซงคิวในรอบเดียวกัน ตัวชี้วัด fairness/inversion ที่เป็นผลหลักของงานวิจัยจะใช้ไม่ได้ทันที

## 2. ลำดับชั้นและกติกาเข้ารอบ

```
FANCLUB      คิว 1  สมาชิก PREMIUM  (+ ลงทะเบียนล่วงหน้า ถ้ารอบกำหนด)
PARTNER      คิว 2  ต้องมีโค้ดสิทธิ์ที่ผูกกับรอบนั้น
MEMBER_ONLY  คิว 3  สมาชิก active ทุกระดับ
PUBLIC       คิว 4  ทุกคน
```

| เหตุผลที่เข้าไม่ได้ | ข้อความที่ผู้ใช้เห็น |
|---|---|
| `ROUND_CLOSED` | ยังไม่ถึงเวลาเปิดขายรอบที่คุณมีสิทธิ์ |
| `NOT_MEMBER` | รอบนี้สำหรับสมาชิกเท่านั้น |
| `NEED_PREMIUM` | รอบนี้สำหรับสมาชิกระดับพรีเมียมเท่านั้น |
| `NEED_PRE_REGISTRATION` | รอบนี้ต้องลงทะเบียนล่วงหน้าก่อนถึงจะกดบัตรได้ |
| `NEED_ACCESS_CODE` | รอบนี้ต้องใช้โค้ดสิทธิ์จากผู้สนับสนุน |

ทุกข้อความต่อท้ายด้วย **"รอบ ... เริ่ม (เวลา)"** ของรอบถัดไปที่ผู้ใช้คนนั้นมีสิทธิ์จริง —
ไม่ปล่อยให้ผู้ใช้เดาว่าต้องรอถึงเมื่อไร (`nextEligibleRound`)

**กติกาที่ห้ามแหก 3 ข้อ**
1. **คอนเสิร์ตที่ไม่มีแถวใน `sale_rounds` เลย = พฤติกรรมเดิมทุกอย่าง** — คอนเสิร์ตเก่าต้องไม่พัง (มี unit test คุม)
2. **รอบผ่อนเพดานตั๋วให้หลวมกว่าคอนเสิร์ตไม่ได้** — `effectiveTicketLimit` = `min(concert, round)` เสมอ
   ถ้ารอบตั้ง 10 ใบขณะคอนเสิร์ตให้ 4 ระบบยังบังคับ 4 (สมาชิกห้ามซื้อได้มากกว่าคนทั่วไป)
3. **ในทุกรอบ คิวยัง FIFO ตามเดิม** — รอบเป็นด่านก่อนเข้าคิว ไม่ใช่ลำดับในคิว

## 3. โครงสร้างข้อมูลที่เพิ่ม

```
Membership.tier               STANDARD | PREMIUM     (แอดมินให้ PREMIUM เท่านั้น)

SaleRound
  audience                    FANCLUB | PARTNER | MEMBER_ONLY | PUBLIC
  requiresPreRegistration     bool
  preRegisterStartAt/EndAt    DateTime?   (ไม่ตั้ง = เปิดจนถึงเวลาที่รอบเริ่ม)
  maxTicketsPerUser           Int?        (null = ใช้ค่าคอนเสิร์ต)
  seatQuota                   Int?        (null = ไม่จำกัดเพิ่มจากที่นั่งจริง)

PreRegistration               1 user 1 ครั้งต่อรอบ (unique [saleRoundId, userId]) + code ปลดล็อก
AccessCode                    code unique ทั้งระบบ · maxUses (null = ไม่จำกัด) · usedCount · expiresAt
AccessCodeRedemption          unique [accessCodeId, userId] — 1 คนใช้โค้ดเดิมซ้ำไม่ได้
```

migration เป็น **additive ล้วน** (`ADD COLUMN` nullable/มี default + `CREATE TABLE` + `ALTER TYPE ... ADD VALUE`)
ไม่มี DROP/UPDATE ข้อมูลเดิม → รันบน DB ที่มีข้อมูลอยู่แล้วได้

## 4. จุดที่บังคับใช้ (ต่อจากตาราง checkpoint ใน [20 §5](20_MEMBERSHIP.md))

| จุด | ไฟล์ | ทำอะไร |
|---|---|---|
| ขอเข้าคิว | `app/api/queue/join/route.ts` | `resolveEntryForUser` → ไม่ผ่านตอบ 403 `ROUND_LOCKED` + บอกเวลารอบถัดไป |
| กดจองที่นั่ง | `app/actions/booking.ts` | เช็คซ้ำ (token คิวอาจได้มาตั้งแต่รอบก่อน) + คำนวณเพดานตั๋วของรอบ |
| สร้าง order | `lib/order-finalize.ts` | บันทึก `Order.saleRoundId` + เช็คโควต้าที่นั่งของรอบ |
| หน้าเลือกที่นั่ง | `app/(public)/concerts/[slug]/seats/page.tsx` | แสดง/บังคับเพดานตั๋วของรอบให้ตรงกับ server |
| ยืนยันการจ่ายเงิน | — | **ไม่เช็ค** (กติกาเดิมจาก [20 §5](20_MEMBERSHIP.md): ตรวจขาเข้าเท่านั้น) |

**เรื่องโควต้ากับ race:** โควต้าที่นั่งเป็นทรัพยากรร่วม "ข้ามผู้ใช้" — advisory lock เดิมผูกกับ (user, concert)
จึงกันไม่ได้ ระบบเลยล็อกเพิ่มต่อ "รอบ" (`pg_advisory_xact_lock('saleround:<id>')`) **เฉพาะรอบที่ตั้งโควต้าไว้**
รอบที่ไม่ตั้งโควต้าไม่เสียคอขวดตอนพีค

## 5. หน้าจอ

### ผู้ใช้ — หน้าคอนเสิร์ต (`components/sale-round-panel.tsx`)
- ไทม์ไลน์รอบทั้งหมด: ชื่อรอบ · ช่วงเวลา · ป้ายสถานะ (เปิด-คุณเข้าได้ / เปิด-ยังไม่มีสิทธิ์ / ยังไม่เริ่ม / จบแล้ว / **โควต้ารอบนี้หมดแล้ว** — rev 43, ดู [23 §9](23_SOLD_OUT.md))
- แผง CTA ข้างปุ่ม "เข้าคิวจองตั๋ว" มีบรรทัดสรุปรอบแบบไม่ผูกผู้ใช้ (`describeRoundTimeline`, อยู่ในหน้าแคชได้): "ตอนนี้: รอบสมาชิก (เฉพาะสมาชิก) · รอบทั่วไป เริ่ม …" (rev 43)
- แถบสรุปบนสุด: "ตอนนี้คุณกดบัตรได้ในรอบ…" หรือเหตุผล + เวลาที่รอบของคุณเริ่ม
- ปุ่ม **ลงทะเบียนล่วงหน้า** (โผล่เฉพาะคนที่ผ่านคุณสมบัติรอบนั้นจริง) → ได้โค้ด `PR-XXXXXXXX`
- ช่องกรอก **โค้ดสิทธิ์** (โผล่เฉพาะเมื่อมีรอบพาร์ทเนอร์ที่ยังไม่ปลดล็อก)
- โหลดผ่าน `GET /api/concerts/[id]/rounds` เพราะหน้าคอนเสิร์ตเป็นหน้าแคช (`revalidate 60`) — สถานะรายบุคคลห้ามติดแคชร่วมกัน

### แอดมิน — หน้าคอนเสิร์ต (`components/admin-sale-rounds.tsx`)
- ตั้งรอบ: ชื่อ · กลุ่มผู้มีสิทธิ์ · ช่วงเวลา · เพดานตั๋ว/คน · โควต้าที่นั่ง · เปิด/ปิดลงทะเบียนล่วงหน้า + หน้าต่างเวลา
- **rev 43:** รอบที่อยู่นอก "ช่วงขาย" ของคอนเสิร์ตไม่มีใครกดถึง (หน้าเว็บโชว์ปุ่มเข้าคิวเฉพาะในช่วงขาย — `lib/concert-display`) →
  `createSaleRound` ขยายช่วงขายให้ครอบรอบอัตโนมัติ (`saleWindowCovering` ขยายอย่างเดียว ไม่หด ไม่เกินวันแสดง) + ปฏิเสธรอบที่จบหลังเวลาแสดง ·
  หน้าแอดมินเตือนเมื่อมีรอบหลุดช่วงขาย (`roundsOutsideSaleWindow`) เช่นหลังแอดมินแก้ "เริ่มขาย" ทีหลัง ·
  พรีเซ็ต "ตั้งรอบให้เลย" ยึดช่วงขายเดิมเป็นรอบทั่วไป (ดู [23 §5](23_SOLD_OUT.md))
- แต่ละรอบโชว์ยอดลงทะเบียนล่วงหน้า + จำนวนคำสั่งซื้อ · ลบได้เฉพาะรอบที่ยังไม่มี order ผูก
- รอบพาร์ทเนอร์: ออกโค้ด (ตั้งจำนวนสิทธิ์ได้) + ดูยอดใช้ `ใช้ไป x/y`
- หน้า `/admin/memberships`: ปุ่ม **ให้พรีเมียม / ลดเป็นมาตรฐาน** (เปลี่ยนระดับอย่างเดียว ไม่พ่วงต่ออายุ)

```bash

```

**ทดสอบบนเครื่องจริง (2026-08-20)** — Postgres/Redis จริง + คลิกผ่านหน้าเว็บทั้งหมด:

| ขั้น | ผลที่ได้ |
|---|---|
| แอดมินสร้างรอบแฟนคลับ (ต้องลงทะเบียนล่วงหน้า, 2 ใบ/คน, โควต้า 10) + รอบทั่วไป | สร้างได้ ค่าลงครบทุกช่อง |
| คนไม่ได้เป็นสมาชิกเปิดหน้าคอนเสิร์ต | "รอบนี้สำหรับสมาชิกเท่านั้น — รอบทั่วไป เริ่ม … 23:00" · ไม่มีปุ่มลงทะเบียน |
| สมาชิก STANDARD ขอเข้าคิว (`POST /api/queue/join`) | **403 `ROUND_LOCKED` / `NEED_PREMIUM`** |
| แอดมินกด "ให้พรีเมียม" | tier เปลี่ยนเป็น PREMIUM · **วันหมดอายุไม่ถูกแตะ** |
| สมาชิก PREMIUM เปิดหน้าเดิม | เหตุผลเปลี่ยนเป็น "ต้องลงทะเบียนล่วงหน้า" + ปุ่มลงทะเบียนโผล่ |
| กดลงทะเบียนล่วงหน้า | ได้โค้ด `PR-GL3CUQFB` · การ์ดเปลี่ยนเป็น "คุณเข้าได้" |
| เข้าคิวผ่านหน้าเว็บจริง | ผ่านด่านรอบ → เข้าคิว → ถูก admit → เข้าหน้าเลือกที่นั่ง |
| เลือก 3 ที่นั่งในรอบที่จำกัด 2 | ถูกปฏิเสธ: "จองได้อีกสูงสุด 2 ที่นั่ง (จำกัด 2 ที่นั่ง/คน ในรอบแฟนคลับ)" |
| จอง 2 ที่นั่ง | order สร้างพร้อม `saleRoundId` = รอบแฟนคลับ · ตัวนับโควต้าขึ้นเป็น 2/10 |
| แอดมินออกโค้ด `MASTERCARD2026` (2 สิทธิ์) แล้วผู้ใช้กรอก `"mastercard2026  "` | normalize แล้วผ่าน · ปลดล็อกรอบพาร์ทเนอร์ · `usedCount` = 1 · ฟอร์มโค้ดหายไป |

**บั๊กที่เจอตอนรันจริงและแก้แล้ว 2 ตัว**
1. ปุ่ม "ลงทะเบียนล่วงหน้า" โผล่ให้คนที่ไม่ได้อยู่ในกลุ่มของรอบ (กดแล้ว server ปฏิเสธเปล่า ๆ) → `describeRounds` เช็คคุณสมบัติก่อนโชว์ปุ่ม
2. รอบที่ปิดลงทะเบียนล่วงหน้ายังเก็บหน้าต่างเวลาค้างจากฟอร์ม → server ล้างเป็น `null` เสมอเมื่อไม่ได้เปิดใช้

## 7. ที่ยังไม่ทำ (ตั้งใจ)

| ไม่ทำ | เหตุผล |
|---|---|
| สมาชิกเสียเงิน / ต่ออายุแบบชำระเงิน | ต้องลากทางเดินเงิน+สลิป+คืนเงินเข้ามาเกี่ยว เสี่ยงกับส่วนที่เป็นเงินจริงโดยไม่ได้เพิ่มค่าเชิงวิจัย |
| โควต้าแยกรายโซน (แฟนคลับได้เฉพาะโซนหน้า) | โควต้าปัจจุบันเป็นระดับรอบ — รายโซนต้องออกแบบ data model เพิ่ม |
| แจ้งเตือนก่อนรอบเปิด (อีเมล/พุช) | ไม่มีระบบคิวงาน/cron สำหรับส่งอีเมลในโปรเจกต์นี้ |
| OTP มือถือ | ค่าใช้จ่ายต่อข้อความ ขัดข้อกำหนด "0 บาท/เดือน" |
| แก้ไขรอบหลังสร้าง (edit) | ตอนนี้ทำได้แค่สร้าง/ลบ — รอบที่มี order ผูกแล้วห้ามลบ (กันยอดขายไร้ที่มา) |
